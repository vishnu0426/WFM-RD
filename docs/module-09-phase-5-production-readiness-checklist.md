# Module 09 Phase 5 Production Readiness Checklist

Honest split between what this phase's code actually delivers and what is genuinely a later phase's work, or a disclosed structural limitation. This phase's own design doc (and ADR-0110) record the single most important interpretive decision in this module's build: a tenant-authored "custom metric" is a named view onto an already-whitelisted column, not an arbitrary formula - a deliberate, disclosed narrowing of what §0.5's "custom formula" phrasing might otherwise suggest, made to honor §0's own non-negotiable rather than to avoid work.

## Delivered in this phase (application code)

- [x] `MetricValidationService.validateAndTier` - structural whitelist check (reusing `SOURCE_VIEW_REGISTRY`, the exact registry `MetricQueryEngineService` already checks at query time), a real bounded dry-run against the replica (RLS-scoped, same read path a live widget uses), and cost-tiering by measured wall-clock duration (disclosed placeholder thresholds, ADR-0110). Rejects outright on either failure - nothing is ever stored with `validatedAt: null`.
- [x] `MetricDefinitionService.createMetricDefinition` - the write path this phase's pipeline needed to have any real effect (§4.1 never named one). Validates first, then checks a tenant-scoped name collision (`MetricNameAlreadyExistsError`, a proactive check, not a caught Postgres error), then inserts via `withTenantConnection`.
- [x] `createMetricDefinition` GraphQL mutation, `MetricDefinitionResult`/`CreateMetricDefinitionInputType`/`CalculationDefinitionInputType`, `MetricCategory` registered as a GraphQL enum.
- [x] `DashboardService`'s widget guard extended: an unvalidated metric (`validatedAt IS NULL`) is rejected the same way an expensive one is - verified directly against a manually-crafted unvalidated row (no real write path can produce one, since `createMetricDefinition` always validates before insert).
- [x] `analytics_metric_definition_validations_total{result, cost_tier}` - real, wired, verified via `/metrics` after a real `createMetricDefinition` call.
- [x] Three new `DomainError` subclasses registered in `DomainErrorFilter`: `MetricValidationFailedError` (400), `UnvalidatedMetricNotAllowedOnWidgetError` (409), `MetricNameAlreadyExistsError` (409).
- [x] Unit test coverage: `MetricValidationService` (whitelist rejection at every level - sourceView, valueColumn, dimension - the real dry-run query shape, cost-tier classification, dry-run-failure rejection, metric recording for both outcomes), `MetricDefinitionService` (validate-before-collision-check-before-insert ordering, name-collision rejection, the validated fields actually persisted), `DashboardService`'s new guard - all mocked-pool/mocked-manager, no live Postgres required (110 tests total, up from 97 in Phase 4).
- [x] Verified against a real local Postgres, the same real streaming replica Phase 2 stood up, and real GraphQL requests: a whitelist-legal `createMetricDefinition` call succeeds, measures `'cheap'`, and its result is immediately queryable via `metricQuery` for the real seeded value (10 overtime hours); an invalid `valueColumn` is rejected with `METRIC_SOURCE_NOT_ALLOWED`; a duplicate name is rejected with `METRIC_NAME_ALREADY_EXISTS`; the unvalidated-metric widget guard was exercised against a real manually-crafted row and correctly rejected.

## Explicitly NOT done here (needs a later phase, or is a disclosed structural limitation)

- [ ] **A tenant cannot author a genuinely new formula/computation** - only a named view onto an already-whitelisted `(sourceView, valueColumn)` pair, per ADR-0110's own decision. This is not a gap to close in a later phase - closing it would mean allowing exactly the kind of re-derivation §0's non-negotiable exists to prevent. Flagged here so a future reader doesn't mistake the narrow scope for an oversight.
- [ ] **No dry-run-tiered metric can currently measure `'moderate'`/`'expensive'`** - every whitelisted source view is a pre-computed, indexed rollup table, so every real dry-run measures well under the `'cheap'` threshold. The classification logic itself is real and tested (`classifyCostTier` has unit coverage for all three tiers via direct duration values), but no *end-to-end* real request has ever produced a non-`'cheap'` result. Revisit once a future source view is added without the same indexing discipline, or once Phase 8's load test suggests different thresholds.
- [ ] **No REST surface for `createMetricDefinition`.** GraphQL only.
- [ ] **`createScheduledExport`.** Phase 6.
- [ ] **`askAnalyticsQuestion`.** Phase 7.
- [ ] **Phase 8's load test**, which is this platform's first real opportunity to check whether the `100ms`/`1000ms` cost-tier thresholds are the right numbers.
