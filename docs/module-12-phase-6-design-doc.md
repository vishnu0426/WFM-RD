# Module 12 Phase 6 Design Doc — Integration Hub: First ACD Connector, Full Streaming Relay Path

**Status:** Approved for implementation
**Owner:** Integration Hub pod (Module 12).
**Scope:** Per §7 — "The first ACD/CCaaS connector (Genesys Cloud recommended per research), the real streaming relay path end to end: terminate the provider's real-time channel, apply `FieldMapping`, forward to Module 05's activity-events endpoint with the backpressure guard from §5a." Concretely: `IntradayActivityEventClient` (the real, HMAC-signed outbound leg to Module 05), `BackpressureQueue` (the bounded, backoff-then-drop outbound guard), `GenesysCloudAdapter` (the real inbound leg - Genesys Cloud's own Notifications API provisioning + WebSocket), and the `StreamingRelayService`/`SyncJobsService` wiring needed for a running session to report its own progress continuously rather than once at the end.

## Problem

Phase 2 built the streaming relay's shape (`StreamingRelayAdapter`, `StreamingRelayService`, `SyncJob` lifecycle for `sync_type: streaming` rows) with zero real adapters registered - a connector whose provider had no adapter failed cleanly, which was correct for that phase but left the entire real data path unbuilt. This phase had to make four genuinely separate things real:

1. **The outbound leg**: Module 05's real `activity-events` endpoint, its actual auth (`HmacSignatureGuard`, not the header/body shape used anywhere else in this platform - `tenantId` is a URL path segment, not a header), and its real degradation signal (`503` → `UpstreamUnavailableError`) versus a genuine per-event rejection - verified live against the actual running service before any client code was written (`docs/module-12-provider-research.md` names REST delivery; the endpoint's exact contract had to be confirmed independently, since the module prompt doesn't specify it).
2. **The backpressure guard** (§5a): "a bounded queue with backoff if Module 05 signals degradation" - real, since a fast-moving presence-event stream with no bound would let one degraded downstream call turn into unbounded memory growth.
3. **The inbound leg**: a real provider. Genesys Cloud was chosen (per the module prompt's own recommendation) as the reference `StreamingRelayAdapter` - real OAuth2 client-credentials auth, real three-call Notifications API provisioning, a real WebSocket client (ADR-0141).
4. **Continuous progress reporting**: §2.1's own comment that a streaming `SyncJob` row's `records_processed`/`records_failed` mean "events forwarded/failed in the window," not "batch totals" - Phase 2's `StreamingRelayAdapter` interface had no way for a running session to report progress incrementally, only at connect/disconnect. This phase extended it with `StreamingRelayCallbacks` and a new atomic `SyncJobsService.incrementCounts`, safe under concurrent increments from a fast stream (a single `col = col + delta` UPDATE, no read-modify-write race).

## Decision

**`IntradayActivityEventClient`** (`src/sync/relay/providers/intraday-activity-event-client.ts`) - HMAC-SHA256 over `${timestamp}.${rawBody}`, `x-agno-webhook-signature: t=<unix_ms>,v1=<hex>`, POSTs to `${INTRADAY_SERVICE_URL}/v1/intraday/tenants/${tenantId}/activity-events`. Reads its per-tenant secret from `INTRADAY_INGESTION_HMAC_SECRETS` (a JSON map, plain shared config - not Vault, ADR-0141). Distinguishes `IntradayUpstreamDegradedError` (real `503`, the backpressure guard's trigger) from `IntradayForwardFailedError` (Module 05 rejected the event body itself - a genuine per-event failure, not upstream degradation) from `IntradayHmacSecretNotConfiguredError` (fails closed if the tenant has no configured secret).

**`BackpressureQueue<T>`** (`src/sync/relay/providers/backpressure-queue.ts`) - a bounded in-memory array (`capacity`), FIFO drain loop. `enqueue()` past capacity drops the *newest* item immediately (`queue_full`, never blocks the caller). A `process()` throw of `IntradayUpstreamDegradedError` retries the *same* item with exponential backoff (`base_ms: 500`, capped `30000ms`) up to `maxDegradedRetries` (default 5), then drops it (`sustained_degradation`) and moves on - an unbounded retry would let one stuck item block every event behind it forever. Every drop is counted via `onDropped`, never silent, per this platform's established "no silent caps" convention.

**`GenesysCloudAdapter`** (`src/sync/relay/providers/genesys-cloud.adapter.ts`) - the reference `StreamingRelayAdapter` (ADR-0141). `connect()`: reads `connector.config.{genesysApiBaseUrl, genesysUserIds, credentialReference}`, reads `{clientId, clientSecret}` from Vault, fetches an OAuth2 client-credentials token, creates a real Notifications API channel, subscribes it to one `v2.users.{id}.presence` topic per configured user ID, opens a `ws`-package WebSocket to the returned `connectUri`. Each inbound frame is filtered (Genesys's own `channel.metadata` heartbeat frames are real and expected, not errors), the `v2.users.{userId}.presence` topic name yields `userId`, `{userId, ...eventBody}` is run through the tenant's own `FieldMapping`s (Phase 3's `applyFieldMappings`, unmodified - no new transform machinery needed), and a complete result is enqueued to a per-connector `BackpressureQueue` whose `process()` calls `IntradayActivityEventClient.forward()`. `sourceEventId` is synthesized as `${connector.id}:${userId}:${modifiedDate}` (Genesys's own `modifiedDate` on every real presence event) - deterministic across a retransmit, which is what lets Module 05's own dedupe absorb a reconnect resending its last-known state. An unexpected WebSocket `close` re-runs the full provisioning dance with exponential backoff, unbounded (ADR-0141) - Genesys's own model does not allow resuming a closed channel.

**`process()`'s own accepted/duplicate handling**: forwarding an event that comes back `duplicate` (Module 05 already counted this exact `sourceEventId`) does **not** call `onEventForwarded()` - counting a deduped retransmit would double-count against this job's own `records_processed`, contradicting §2.1's "events forwarded in the *window*" semantics. This was a real bug caught live (see Verification) - the first implementation called `onEventForwarded()` unconditionally on any non-throwing result.

**`StreamingRelayCallbacks`/`SyncJobsService.incrementCounts`** - `StreamingRelayService.start()` builds `{onEventForwarded, onEventFailed}` and passes them into `adapter.connect()`; each fires an atomic `UPDATE ... SET records_processed = records_processed + 1` (or `records_failed`), scoped by `withTenantConnection`, fire-and-forget with a logged warning on failure (a lost increment is a stats accuracy issue, not a correctness issue for the event itself, which has already been forwarded or dropped by that point).

## Verification

**Unit**: `backpressure-queue.spec.ts` (6 tests) - in-order processing, `queue_full` drop while at capacity, degraded-retry-then-recover with a real fake-clock-free backoff (`backoffMs: () => 0`), `sustained_degradation` drop after `maxDegradedRetries` with the queue continuing to the next item, a genuine (non-degradation) error moving on without retrying, `stop()` halting further draining.

**Real end-to-end** (`test/integration/genesys-cloud-adapter.spec.ts`, real Postgres + real Vault + a real local HTTP+WebSocket server standing in for Genesys Cloud's actual API surface + the REAL, already-running `intraday-service`):
- The real three-call provisioning dance actually happens - asserted from the fake server's own recorded state (`subscribedTopics`), not just "a WebSocket eventually appeared."
- A real presence frame relays end to end into Module 05's own live state, confirmed by reading it back through Module 05's real `agentLiveState` GraphQL query (async, NATS-consumer-mediated on Module 05's side - polled, not asserted immediately).
- **Idempotency**: the identical frame retransmitted does not increment `records_processed` a second time (this caught the accepted/duplicate bug above - the test failed with `records_processed: 2` against the first implementation, and passed once `process()` was fixed to only count `status: 'accepted'`).
- **Real backpressure**: a burst of 20 distinct events (deliberately spaced 1ms apart in their synthesized `modifiedDate` - a first version of this test used `new Date()` per iteration inside a tight synchronous loop, which produced duplicate timestamps across several frames since a JS loop resolves faster than the Date clock's own millisecond granularity, silently turning most of the "backpressure" burst into idempotent duplicates instead of genuinely exercising `queue_full`) against a `backpressureQueueCapacity: 2` connector - confirms `records_failed > 0` via real `queue_full` drops, not simulated.
- Clean `relayService.stop()` closes the WebSocket and completes the `SyncJob`; the test's own cleanup terminates any still-open WebSocket client before `wss.close()`, since a client left open (e.g. by an assertion throwing before `stop()` runs) would otherwise hang the fake server's shutdown indefinitely rather than just failing that one assertion - a real hang encountered while first writing this test, fixed with a `try`/`finally` around the scenario and an explicit client-termination step in `afterAll`.

**Full suite**: 61 unit tests + 31 integration tests (8 suites each), `typecheck`/`lint` clean.

## Rollback plan

Revert this phase's commits, including `sync.module.ts`'s provider registration back to `{ provide: STREAMING_RELAY_ADAPTERS, useValue: [] }`. `StreamingRelayService.start()` falls back to Phase 2 behavior (any `acd` connector fails cleanly with `no_adapter_registered`, exactly as before this phase). No other phase's code depends on this one.

## Explicit assumptions (spec was ambiguous or silent here)

1. **The streaming relay terminates each provider's own native transport, not a generic webhook receiver** (ADR-0141) - the module prompt's shared HMAC-signing convention across §5d's webhook framework and §2.2 rule 3b's activity-events forwarding could read as "one webhook shape everywhere"; the provider research doc makes clear no researched ACD provider actually delivers real-time state that way.
2. **`genesysUserIds` is tenant-supplied config, not auto-discovered** - restates ADR-0138's crosswalk gap for streaming; no code anywhere in this adapter enumerates a tenant's Genesys agents.
3. **Reconnect-on-close is unbounded** (exponential backoff capped at a 30s interval, but never gives up) - a deliberate choice given Genesys channels are not resumable and a human operator, not silent abandonment, is the intended response to a permanently broken connector. Contrast with `BackpressureQueue`'s bounded per-item retry, made explicit in ADR-0141.
4. **A `duplicate` forward result is a no-op for `SyncJob` counters** - neither `records_processed` nor `records_failed` - since it is neither a new forward nor a failure, just Module 05's own dedupe absorbing an expected retransmit.

## Out of scope for this phase (do not build yet)

- Remaining streaming/batch connector types named in §7's own Phase 6b (SAP SuccessFactors, ADP, Salesforce, NICE CXone, Five9, Talkdesk, and the Avaya Aura/CMS scope decision) - each is real, provider-specific client work per ADR-0141, not a config variant of `GenesysCloudAdapter`.
- `WebhookSubscription`/`WebhookDelivery`, the outbound webhook dispatcher - Phase 7.
- Connector health dashboard, remaining GraphQL surface for streaming session status, dashboards/runbooks - Phase 8.
- A shared (Redis-backed) rate/concurrency limiter for the streaming leg - Genesys's own `concurrent_request_limit` was repurposed by ADR-0135 as "max WebSocket channels," a provisioning-time constraint (one channel per adapter connection here), not a per-request throttle this phase's single-channel-per-connector design needs to enforce.
- Multi-instance/restart-safe relay ownership - `StreamingRelayService.liveSessions` is process-local, in-memory state (documented in Phase 2's own doc comment); unchanged by this phase.
