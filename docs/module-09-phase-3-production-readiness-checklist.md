# Module 09 Phase 3 Production Readiness Checklist

Honest split between what this phase's code actually delivers and what is genuinely a later phase's (or a different module's) work. This phase's own design doc records the single largest disclosed deviation from the source spec in this module's build so far - `mv_cost_vs_budget` cannot honestly report a dollar figure, because no pay-rate or budget capability exists anywhere in this platform (ADR-0109) - fixed by shipping what the data actually supports and naming the gap precisely, not by fabricating a number.

## Delivered in this phase (application code)

- [x] `1700006000000-CostVsBudgetAttritionBySiteTables.ts`: `analytics_mv.mv_cost_vs_budget`/`mv_attrition_by_site`, both RLS-protected (real tenant data, unlike `mv_lineage`), both `SELECT`-only to `agno_analytics_app`. Amends both views' `mv_lineage.source_description` to what this phase actually ships.
- [x] `MvCostVsBudgetRefreshJobService` - a `@Cron('0 3 * * *')` job joining `org.employees.cost_center` × `scheduling.shift_assignments` × `attendance_leave.leave_request` (three schemas, one query, via the replica pool) and upserting `scheduled_hours`/`overtime_hours`/`approved_leave_days` via the primary pool. **No dollar column of any kind** - verified by a dedicated unit test asserting the generated SQL contains neither `cost` nor `budget` as a column name.
- [x] `MvAttritionBySiteRefreshJobService` - a `@Cron('30 3 * * *')` job joining `org.employees.termination_date` to its nearest `type = 'site'` `org.org_units` ancestor via the `path` ltree column's `<@` operator, upserting `terminations_count` only.
- [x] Both jobs reuse Phase 2's `RefreshModule`/pool providers/`mv_lineage`-update shape unchanged - no new pool, no new role, no `app.module.ts` change.
- [x] `data_as_of` sourced from each job's own real observation timestamp (`shift_assignments.updated_at`/`leave_request.decided_at` for cost-vs-budget, `employees.updated_at` for attrition) - Phase 2's own bug-class fix (never a nominal date/period boundary) applied consistently here from the start, not rediscovered.
- [x] ADR-0109: the full reasoning for why `mv_cost_vs_budget` reports hours/days, confirmed by inspecting every schema in this platform for a pay-rate or budget column/table (none exists), not assumed from the source spec's silence.
- [x] Unit test coverage: migration shape (RLS, upsert keys, `SELECT`-only grants, and an explicit assertion that `mv_cost_vs_budget`'s DDL contains no dollar-shaped column), both refresh jobs' query/upsert/transaction/failure-marking logic - all mocked-pool, no live Postgres required (60 tests total, up from 44 in Phase 2).
- [x] Verified against a real local Postgres and the same genuine streaming replica Phase 2 stood up: both jobs computed real, hand-verified numbers from real seeded cross-module data (26 scheduled hours, 10 overtime hours, 3 approved leave days, 1 termination correctly attributed to the correct site); RLS isolation and the `SELECT`-only grant were both confirmed directly (`permission denied` on a `DELETE` attempt); the full app boots with all four refresh jobs registered and serves `/healthz`/`/readyz`/`/metrics`.

## Explicitly NOT done here (needs a later phase, or a different module entirely)

- [ ] **A real dollar cost-vs-budget comparison.** This is not a Phase 4+ TODO for this module - it requires a pay-rate capability (most naturally new columns on `org.employees`, owned by Module 02) and a budget-allocation entity (owned by whichever module is judged the right owner), neither of which exists anywhere in this platform today. Building either is new, separately-scoped cross-module work with its own ADR - see ADR-0109's own Consequences section.
- [ ] **A real attrition rate.** Needs historical point-in-time headcount reconstruction via `org.employee_history` - not attempted this phase, named as a gap in the design doc.
- [ ] **Working-day-aware or month-boundary-split leave-day attribution** in `mv_cost_vs_budget`. Calendar days, attributed wholly to a request's start month - a disclosed simplification (ADR-0109), not a bug to file, though a future phase could revisit it with its own ADR if a real need surfaces.
- [ ] **Any request path reading either new table.** `agno_analytics_app` has `SELECT` on both; nothing calls it yet - no GraphQL, no REST, no query engine exists in this service. Phase 4.
- [ ] **The custom-metric validation pipeline, BI connector, async exports, the NL query bridge, the §0.5 load test, the consistency-check job.** Unchanged from Phase 1/2's own list - Phases 5–8.
- [ ] **Real, consistent cross-module test data in any actual deployment.** This phase's verification seeded a small, internally-consistent fixture chain (`forecast_run`/`schedule_job`/`schedule`/`shift_assignments`, `leave_type`/`leave_request`, one termination) into the shared local dev database specifically because the pre-existing fixtures across `org`/`scheduling`/`attendance_leave` (each generated independently by prior modules' own verification work) shared no consistent employee/tenant IDs. Neither the pre-existing nor the newly-seeded rows are production data.
