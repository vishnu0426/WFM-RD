# ADR-0138: `FieldMapping` renames and transforms field *values*, not cross-system *identifiers* — org unit/entity IDs must already align

## Context
Building the first real batch adapter (`WorkdayAdapter`, Phase 3) surfaced a real limitation in `FieldMapping`'s shape (§2.1): `source_field` → `target_field` plus an optional `transformation_rule` (jsonb) is a field-renaming-and-value-transform mechanism — proven in this phase to handle enum translation (`"Full-Time"` → `"full_time"` via `valueMap`) and unit conversion (an FTE fraction → hours/week via `multiply`, `src/sync/batch/providers/field-mapping-transform.ts`). It has no mechanism to translate an *identifier* from the source system's own ID space into Agno WFM's UUID space — e.g. Workday's own organization/department identifier for a worker's org unit is not the same value as Module 02's `org_unit.id` UUID, and nothing in `FieldMapping`'s schema or `transformation_rule`'s jsonb shape provides a lookup table (`external_org_code → agno_org_unit_uuid`) to bridge that gap.

This matters concretely for `orgUnitId`: Module 02's bulk-import (`POST /v1/employees/bulk-import`) validates that `orgUnitId` is a real, existing org unit for the tenant — a raw Workday organization code passed straight through would be rejected as a conflict on every record, not just fail silently.

## Decision
Phase 3 does not build an identifier-crosswalk mechanism. `WorkdayAdapter`'s own real end-to-end verification (`docs/module-12-phase-3-design-doc.md`) uses fixture data where the source system's own organization identifier field *is* the real Agno `org_unit.id` UUID — framed explicitly as "this tenant's Workday export was configured to emit Agno-compatible org unit ids," a real-world pattern some customers already use (aligning source-system codes to the target system during their own export configuration), not a fabricated shortcut. `FieldMapping` continues to do exactly what it does today: rename a field and optionally transform its *value* via `valueMap`/`multiply` — both of which operate on a single record's own field values, never a cross-record or cross-system lookup table.

## Consequences
- Any tenant whose real Workday (or other HRIS/payroll/CRM) org/department codes do **not** already match Agno's own `org_unit.id` UUIDs cannot successfully sync org-unit-bearing records through this module yet. This is a real, disclosed onboarding gap for such tenants, not a hypothetical edge case — most real customers' source-system codes will *not* happen to be Agno UUIDs.
- A real fix needs a genuine crosswalk table (e.g. a new `FieldMapping`-adjacent lookup: `(connector_id, source_value, target_value)` rows, or a `transformation_rule` shape like `{"lookup": {"WD-ORG-100": "9ed1b40a-..."}}`) — either is a real, scoped schema/logic addition for a future phase (Phase 4, alongside `FieldAuthorityPolicy`, is the natural home, since both are about making field-level data trustworthy before it reaches Module 02), not something to retrofit silently into `transformation_rule`'s current two shapes without its own design pass.
- `valueMap` (already built) is structurally the closest existing primitive to a crosswalk — the difference is only that today's usage maps a small, fixed enum (4-5 known values) inline in `transformation_rule`, not an open-ended per-tenant lookup table that would need its own storage rather than living in one jsonb column per mapping. Worth noting as the natural extension point when this gap is actually closed.
- This module's other named batch providers (SAP SuccessFactors, ADP, Salesforce) will hit the identical gap for their own org/cost-center/department identifiers — this is a platform-wide limitation of the current `FieldMapping` shape, not something specific to Workday.
