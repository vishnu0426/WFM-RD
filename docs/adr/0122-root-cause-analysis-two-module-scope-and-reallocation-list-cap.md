# ADR-0122: `rootCauseAnalysis` scoped to two modules (compliance + intraday), not three — and why `ListReallocationsForPeriod` is a capped list, not a stream

## Context
§9 Phase 4 names "the multi-gRPC-call `root_cause_analysis` path" without specifying which modules or what query shape. Two design questions needed real answers, not guesses:

1. **Which modules, and keyed by what?** A natural three-source scenario ("why is adherence low for org unit X") would pull Module 08 (adherence), Module 05 (reallocation/queue disruption), and Module 03 (forecast accuracy for the same org unit/period) - but `ForecastExplanationDataService.GetForecastRunForExplanation` (ADR-0119) is keyed by `forecast_run_id`, not `org_unit_id`+period, and there is no "find the forecast run for this org unit/period" lookup anywhere in this platform. Adding one was weighed and rejected for this phase: it's a real, separate gap (which run is "the" run for an org unit/period when several could exist) that deserves its own ADR when a real caller needs it, not a guess bolted onto this one.
2. **How does Module 10 find "which reallocations happened in this org unit/period"?** `ReallocationAction` (ADR-0070) has no `org_unit_id` column - it's keyed by `from_queue_id`/`to_queue_id`. A genuinely org-unit-scoped query would need a queue-to-org-unit lookup that doesn't exist either.

## Decision
- **`rootCauseAnalysis(orgUnitId, periodStart, periodEnd)` combines exactly two sources**: Module 08's `AdherenceRollupService.GetOrgUnitAdherenceSummary` (ADR-0121, real org-unit+period keying) and Module 05's new `ReallocationService.ListReallocationsForPeriod` (below) - **tenant-wide, not org-unit-filtered**, disclosed as a real, named scope limitation in both the proto's own doc comment and this ADR, not silently treated as org-unit-scoped when it isn't.
- **Neither source having data is not, by itself, an error** - a quiet period with zero reallocations, or an org unit with no `AdherenceScore` rows yet, are both legitimate outcomes. `RootCauseAnalysisNoDataError` (mapped to 404) only fires when BOTH sources have nothing at all - the one case where there is genuinely nothing to ground an LLM call in (non-negotiable #2).
- **`ListReallocationsForPeriod` is unary with a capped, newest-first result (100 rows) plus a disclosed `total_matched_before_cap`**, not server-streaming - deliberately simple, since this is intraday-service's first gRPC surface of any kind (ADR-0120) and a tenant's reallocation volume in one period is nowhere near `EmployeeService.GetSchedulableEmployees`' 100k+-employee scale that justified streaming elsewhere in this platform. §8's "no silent caps" convention is honored by the explicit count field, not by pretending the cap doesn't exist.
- **§5.1's tenant-scoping assertion is asymmetric across the two sources, on purpose**: the adherence source echoes a real `tenant_id` from a scored row (asserted against); the reallocation list has no natural per-row `tenant_id` to assert against a single time (it's already constrained by an explicit `tenant_id` WHERE clause plus RLS at the source, the same defense-in-depth RLS already provides for every other query in this platform) - documented as a deliberate asymmetry in `RootCauseAnalysisService`'s own code, not an oversight.

## Consequences
- This is the first interaction type whose `assertSameTenant` call passes a real, populated multi-fact array in production code (Phase 3's own test coverage proved the mechanism works with 2+ facts; this is the first real caller) - though in practice today it's a 0-or-1-element array, since only one of the two sources (adherence) has a per-row tenant fact to assert. A future third source with its own per-row tenant fact would exercise the true 2+-fact path for real.
- If a real "forecast run for this org unit/period" or "reallocations for this org unit" lookup is built later (closing either gap named above), `rootCauseAnalysisService` is the natural place to add that third source - not a redesign, an additive `Promise.all` entry plus one more `TenantScopedFact`.
- 42 unit tests across this module's four interaction-type services, all passing; a live boot with the full multi-client dependency graph resolving correctly, GraphQL schema inspected directly and confirmed correct (`rootCauseAnalysis(orgUnitId: ID!, periodEnd: DateTime!, periodStart: DateTime!): AIInteraction!`).
