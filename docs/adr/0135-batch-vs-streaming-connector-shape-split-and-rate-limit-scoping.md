# ADR-0135: Batch vs. streaming connector shape split — rate-limit scoping and `concurrent_request_limit` repurposing

## Context
Module 12 v1 treated every external connector as one shape: a cron-scheduled `SyncJob` writing through a batch API. Naming Avaya explicitly (as both AXP and Aura/CMS) in v2 surfaced that ACD/CCaaS providers are not a batch-with-a-shorter-interval variant — they are structurally different, and forcing them onto the batch runner would silently reintroduce the latency Module 05 was built to eliminate. The provider research in `docs/module-12-provider-research.md` makes the split concrete rather than theoretical: not one HRIS/payroll/CRM provider researched (Workday, SAP SuccessFactors, ADP, Salesforce) exposes a push/event-stream mechanism suited to real-time delivery — they are REST/SOAP/OData request-response APIs with a genuine per-request or per-window quota. Conversely, not one ACD/CCaaS provider researched (Genesys Cloud, NICE CXone, Five9, Talkdesk, Avaya AXP) exposes its real-time agent-state data as a request-quota-gated REST resource — the mechanisms are WebSocket topic subscriptions (Genesys, Avaya AXP), long-polling (NICE CXone), session-based WebSocket push (Five9), or Server-Sent Events (Talkdesk). This is a second, independent finding beyond the write-path split already established in §0/§2.2 rule 3: the *inbound acquisition* mechanism, not just the *outbound write target*, differs by connector shape.

This also surfaced that `ProviderRateLimitConfig`'s `requests_per_window`/`window_seconds` columns (§2.1) are a genuine mismatch for the streaming shape. Two providers (Genesys Cloud: max 20 channels/1,000 topics-per-channel; NICE CXone: 100 concurrent requests, uniform default) publish a real concurrency ceiling with no meaningful per-second request rate to pair it with. Two more (Five9, Avaya AXP) publish no rate-limit figure of either kind. Avaya Aura/CMS (on-prem) doesn't have a "requests" concept at all — its constraint is licensed concurrent TSAPI sessions or ODBC connections, a deployment-tier constant, not a request rate.

## Decisions
**The batch/streaming split is this module's second central non-negotiable, alongside the API-only write path (§0/§2.2 rule 3).** A connector's `connector_type` (`hris`/`payroll`/`crm` vs. `acd`) determines its entire acquisition mechanism, not just its target API: batch connectors run on the cron sync runner against `ProviderRateLimitConfig`'s quota-throttle semantics; ACD connectors run on the persistent relay process against backpressure semantics. There is no provider in the researched set that needs both, and no code path should let an ACD connector be scheduled on the batch runner or a batch connector be attached to the relay.

**`ProviderRateLimitConfig.concurrent_request_limit` is repurposed for streaming providers, and this repurposing is explicit, not implicit.** For batch providers (ADP, Salesforce), it means what its name says — a genuine concurrent-in-flight-HTTP-request ceiling, paired with `requests_per_window`/`window_seconds`. For streaming providers, it is redefined per-provider to whatever concurrency unit that provider actually gates: Genesys Cloud → max WebSocket channels (20); NICE CXone → max concurrent connections (100, the one number NICE publishes as a hard, vendor-confirmed cap); Avaya Aura/CMS (if built, per §5c) → licensed TSAPI sessions or ODBC connections, a per-tenant-deployment constant rather than a platform default. Where a streaming provider publishes neither a rate nor a concurrency number (Five9, Avaya AXP — confirmed absent from public docs, not merely hard to find), `requests_per_window`, `window_seconds`, and `concurrent_request_limit` are all seeded `null`, and the real constraint lives entirely in `backoff_strategy` as a self-imposed relay-side cap with an explicit `is_published: false` marker — the schema must not imply a vendor guarantee that doesn't exist.

**Rate-limit scoping is per-connector-pair for every batch provider researched, with one structural exception.** Workday, SAP SuccessFactors, and Salesforce's published/proxy limits are stated per tenant-org or per-API-client — consistent with scoping the token-bucket limiter at `(tenant_id, connector_id)`, as §5a specifies. ADP is the exception worth naming explicitly: its concurrency cap is documented as substantially lower per-node (~12-13) than the aggregate figure (50), meaning the real throttle-scoping decision for ADP isn't purely `(tenant_id, connector_id)` — it also depends on how the sync runner's outbound calls distribute across ADP's gateway nodes, which this module doesn't control. Seed ADP's proactive throttle at the per-node figure, not the aggregate, so the sync runner stays under the tighter real constraint rather than the more permissive documented ceiling.

**Streaming backpressure guards the relay's outbound leg to Module 05, never the provider-facing inbound leg.** Since ACD providers call into or stream at this module rather than being polled on a schedule, the proactive-throttle pattern built for batch providers has no inbound target here. The bounded-queue-with-backoff-on-Module-05-degradation design (§5a) is a different mechanism serving a different failure mode (a burst from the provider side, e.g. a TSAPI/AES link or an AXP WebSocket resuming after an outage and replaying buffered state) than a provider-quota throttle (a self-inflicted burst from this module's own polling cadence). Building one where the other is needed would misdiagnose which side of the connection is actually at risk of being overwhelmed.

## Consequences
- `SyncJob.sync_type: streaming` rows (§2.1) never populate from a rate-limiter-triggered `partial_failure` the way a batch job does — a streaming connector's degraded state shows up as relay connection health (dropped/reconnecting) or forward-failure rate to Module 05, not as a throttle-driven incomplete sync window. The health dashboard (Phase 8) needs genuinely distinct views for these, not one status enum stretched across both.
- The `backoff_strategy` jsonb column carries materially different shapes across providers researched: `{type: "header_driven", header: "Sforce-Limit-Info", ...}` for Salesforce, `{type: "respect_retry_after", channel_topic_cap: 1000, ...}` for Genesys, `{type: "exponential", is_published: false, ...}` for Five9/Avaya AXP. Any code reading this column must treat it as provider-adapter-interpreted config, not a fixed shared schema — a generic backoff executor that assumes every row has the same keys will break on the first provider that doesn't publish a `Retry-After` header.
- This ADR does not decide whether Avaya Aura/CMS's non-REST worker gets built (§5c, §8 explicitly leave that as a separate resourcing call) — it only establishes that *if* built, its `ProviderRateLimitConfig` row follows the same repurposing pattern as the other streaming providers rather than being forced into the batch shape's `requests_per_window` semantics.
