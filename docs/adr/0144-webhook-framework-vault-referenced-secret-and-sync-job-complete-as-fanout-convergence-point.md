# ADR-0144: Webhook framework reuses Module 01's fan-out shape, with a Vault-referenced secret and `SyncJobsService.complete()` as the convergence point

## Context

§2.1 already gave this module `WebhookSubscription`/`WebhookDelivery` tables (Phase 1) with a shape close to, but not identical to, Module 01's own webhook framework (`core.webhook_subscriptions`/`core.webhook_deliveries`, ADR-0046): `WebhookSubscription.secret_reference` (a Vault reference key) where Module 01 has `secret` (plaintext); `WebhookSubscription.status` (`active`/`failing`/`disabled`) plus `consecutive_failure_count` where Module 01 has a bare `is_active` boolean; and `WebhookDelivery` with no terminal-status column at all (`delivered_at` nullable, `retry_count`) where Module 01 has an explicit `status` enum including `dead_lettered`. Nothing in this module names *what* triggers a webhook delivery - Module 01's own answer (`WebhookFanoutService.fanOut`, called from `CoreOutboxPublisherService.drain` right after a successful NATS publish) is the only precedent this platform has for "how does an internal domain event become an external webhook," and this module has its own single canonical "something real just happened" moment: a `SyncJob` reaching a terminal state, whether from a batch run or a streaming session window closing.

## Decision

**Secret storage**: Vault-referenced, not plaintext, extending ADR-0134's discipline to this table too. `WebhookSubscriptionsService.create()` generates a random secret (`randomBytes(24).toString('base64url')`, same shape Module 01 uses), writes it to Vault at `integration-hub/{tenantId}/webhook/{id}/secret`, stores only the reference, and returns the raw secret exactly once in the mutation response - `WebhookDeliveryDispatcherService` re-reads it from Vault on every single delivery attempt (never cached), a real per-delivery Vault round trip Module 01's plaintext-column design doesn't need. Justified specifically because this module's own §0 framing already calls it "the platform's largest external-attack-surface concentration" - repeating Module 01's own flagged plaintext gap here would compound exactly the risk that framing exists to call out.

**Delivery has no terminal status column** - `deliveredAt IS NOT NULL` means delivered; a row that has exhausted `MAX_DELIVERY_ATTEMPTS` (5, matching Module 01's own `MAX_ATTEMPTS_BEFORE_DEAD_LETTER`) simply stops matching `WebhookDeliveriesService.findPendingBatch`'s own `retry_count < 5` filter - dead-lettering is implicit in the query, not a written state.

**Subscription health is two-threshold, not one boolean**: `FAILING_THRESHOLD = 5` flags a subscription for operator visibility (still attempted every tick); `DISABLED_THRESHOLD = 20` stops the dispatcher from attempting it at all (`WebhookFanoutService`'s own fan-out query excludes `status = disabled`, and `WebhookDeliveryDispatcherService.attemptDelivery` also skips - not double-attempts - a delivery that was queued before a disabled transition landed). A single success resets `consecutive_failure_count` to zero and reverts `failing` back to `active` - self-healing, since a transient receiver outage shouldn't cost a tenant their subscription permanently, only a sustained one should.

**`SyncJobsService.complete()` is this module's own `CoreOutboxPublisherService.drain`** - the single convergence point every real `SyncJob` completion (batch `full`/`incremental`, streaming start-failure, streaming stop) already funnels through, extended to publish `agno.integration_hub.sync_job.completed.v1` to a newly-provisioned real JetStream stream (`AGNO_INTEGRATION_HUB_EVENTS`, `scripts/provision-nats-streams.ts`) and immediately fan out webhook deliveries for it - both best-effort, caught and logged, never allowed to fail the actually-durable `SyncJob` write itself. This is a deliberate architectural choice to put the hook in the shared service rather than duplicating it at each of the (currently five) call sites across `BatchSyncRunnerService`/`StreamingRelayService` that call `complete()`.

## Consequences

- Every integration test in this suite that constructs a real `SyncJobsService` now also needs its two new dependencies (`IntegrationHubNatsClientService`, `WebhookFanoutService`) constructed for real - centralized in one test helper (`test/integration/helpers/real-sync-jobs-service.ts`) rather than duplicated in the 11 files that needed it, with an explicit cleanup function each test's `afterAll` must call. A real bug surfaced writing this: an undrained `IntegrationHubNatsClientService` connection left the whole suite's Jest process alive well after every test had finished - the identical class of hang the Genesys Cloud adapter's own WebSocket cleanup bug was (Phase 6's design doc), on a different transport.
- A tenant sees only one event type from this module today (`sync_job.completed`) - no per-connector-type or per-provider event granularity, since `SyncJobsService.complete()` doesn't know which adapter produced the outcome it's completing, only the `SyncJob` row's own fields (`connectorId`, `syncType`, `status`, counts, `errorDetails`). A consumer that needs provider/connector-type context can query `connectors` themselves, keyed by the delivered `connectorId`.
- The dispatcher reads Vault once per delivery attempt, not once per subscription per tick - a real, accepted cost of never caching credential material outside Vault, consistent with every other adapter in this module.
- `webhookSubscriptions` (a plain list query, secret never included) is a real addition beyond `IntegrationHubGraphQLModule`'s own literal deferred-item list (`triggerManualSync`, `createWebhookSubscription`, `testWebhook`, `webhookDeliveries`) - flagged explicitly, matching this platform's "disclose an addition beyond literal spec text" convention, not silently included.
