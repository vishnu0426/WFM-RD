# ADR-0141: The streaming relay terminates each ACD provider's own real-time transport, not a generic inbound webhook

## Context

§2.2 rule 3b requires every streaming (`acd`) event to reach Module 05 via its real `POST /v1/intraday/tenants/:tenantId/activity-events` endpoint, HMAC-signed the same way Module 12's own webhook framework signs things (§5d). Read quickly, that could suggest the ACD side of this module is also "a webhook" - one inbound receiver shape, symmetric with the outbound leg. `docs/module-12-provider-research.md`'s own per-provider research (sourced before any Phase 6 code was written) says otherwise: of the five researched ACD/CCaaS providers, **none** deliver real-time agent state over a classic webhook. Genesys Cloud uses a WebSocket + topic pub/sub Notifications API; NICE CXone uses long-polling (with a newer WebSocket SDK); Five9 uses a session-authenticated WebSocket; Talkdesk uses Server-Sent Events. A provider-agnostic "webhook receiver" for this side of the module would have nothing to receive from any of them.

## Decision

`StreamingRelayAdapter.connect()` (`src/sync/relay/streaming-relay-adapter.ts`) is a real, provider-terminated client, not a webhook controller - each adapter is responsible for authenticating to and holding open whatever real-time transport its provider actually uses. `GenesysCloudAdapter` (`src/sync/relay/providers/genesys-cloud.adapter.ts`), the first and reference implementation, does the real three-call Genesys Cloud Notifications API provisioning dance (OAuth2 client-credentials token → `POST /api/v2/notifications/channels` → `PUT .../subscriptions`) and then opens a real WebSocket (the `ws` package - Node's native global `WebSocket` lacks usable ambient types in this project's current `@types/node`) to the returned `connectUri`.

Symmetrically, the *outbound* leg to Module 05 (`IntradayActivityEventClient`, `src/sync/relay/providers/intraday-activity-event-client.ts`) is exactly the module's own webhook-style HMAC convention (`x-agno-webhook-signature: t=<unix_ms>,v1=<hex>` over `${timestamp}.${rawBody}`) - Module 12 is the caller here, and it doesn't matter to Module 05 whether the event originated from a real webhook or, as for every researched ACD provider, a WebSocket/SSE/long-poll session this module's own relay terminated. The HMAC convention is shared; the inbound transport is not.

## Consequences

- **Every future ACD adapter is real client code for that provider's actual transport**, not a config-driven variant of one generic receiver. NICE CXone's adapter will hold a long-poll loop or its newer WebSocket SDK; Talkdesk's will hold an SSE client. This is real, provider-specific integration work each time (Phase 6b), not boilerplate - `StreamingRelayAdapter`'s own contract (`connect`/`disconnect`, `StreamingRelayCallbacks`) is the only thing shared across them.
- **No real Genesys Cloud org exists in this environment.** Verification (`test/integration/genesys-cloud-adapter.spec.ts`) runs against a real local HTTP+WebSocket server that speaks the exact three-call provisioning shape plus a real WebSocket upgrade - not a mock of `GenesysCloudAdapter` itself, a real double for the vendor's own API surface, the same posture `WorkdayAdapter`'s Phase 3 verification already established for a REST provider.
- **Reconnect is real and unbounded by design, not bounded like a per-item retry.** A closed/expired Genesys channel is not resumable (Genesys's own model), so an unexpected `close` re-runs the full provisioning dance with exponential backoff (capped at 30s between attempts) rather than a bare socket reconnect - and it never gives up. This is a deliberate asymmetry with `BackpressureQueue`'s own per-item `maxDegradedRetries` (which *does* give up and drop, so one stuck event can't block the stream forever): a permanently unreachable Genesys endpoint should keep announcing itself via repeated `WARN` logs for an operator to notice and fix, not silently abandon the connector. The initial `connect()` call itself does not swallow failures the same way - a structural problem (bad config, no credential, the provider rejecting the request outright) fails the `SyncJob` atomically via `StreamingRelayService`'s existing `adapter_connect_threw` path, matching `WorkdayAdapter`'s posture of not silently retrying a config error.
- **The `genesysUserIds` crosswalk gap is ADR-0138's gap restated for streaming.** There is no discovery call anywhere in this adapter that enumerates "every agent" from Genesys - the tenant supplies the exact Genesys user IDs to subscribe presence for, in `connector.config.genesysUserIds`, and each is asserted to already be a valid Module 02 employee UUID (`ActivityEventDto.employeeId` is `@IsUUID()` on Module 05's own side). The same "source IDs must already align" posture ADR-0138 accepted for batch `employeeNumber`, made concrete for streaming.
- **A shared HMAC secret, provisioned out-of-band, is a real operational requirement.** Module 12's `INTRADAY_INGESTION_HMAC_SECRETS` and Module 05's `INTRADAY_WEBHOOK_SECRETS` must carry the identical `{tenantId: secret}` value for a tenant before streaming works at all - this is plain shared config (an env var on both sides, per `intraday-service`'s own existing convention), not Vault-mediated, and not provisioned by any code either module runs. Missing it fails closed (`IntradayHmacSecretNotConfiguredError`), never silently.
