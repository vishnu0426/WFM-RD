# ADR-0110: a tenant-authored `MetricDefinition` is a named view onto an already-whitelisted source-view column, not an arbitrary formula — the dry-run/cost-tiering gate validates that, cost-tiers it by measured dry-run latency, and rejects anything else

## Context
§0.5/§2.3 rule 2 describes this phase's job as validating a "tenant-authored `calculation_definition`" and cost-tiering it before it can back a live widget - framed around the risk of "a malformed or expensive custom formula" silently degrading platform-wide query performance. Implementing this surfaced a question the source spec never actually answers: **what can a tenant-authored `calculation_definition` actually contain in this platform's real architecture?**

Phase 4's `MetricQueryEngineService` already validates every `calculationDefinition.sourceView`/`valueColumn` against `SOURCE_VIEW_REGISTRY` - a hardcoded whitelist of exactly the four `analytics_mv.mv_*` tables and their real columns - before building any SQL, for any `MetricDefinition`, platform-authored or not. There is no code path, anywhere in this service, that turns an arbitrary jsonb blob into a dynamically-constructed SQL expression - `SOURCE_VIEW_REGISTRY` is not a security boundary layered on top of a more powerful formula language; it *is* the entire vocabulary. A tenant cannot express "average adherence weighted by headcount" or "cost per FTE" - only "this already-computed column, filtered by these already-supported dimensions."

This is a direct, and correct, consequence of §0's own non-negotiable: Module 09 "does not re-derive, re-interpret, or independently recompute a number another module has already computed." An arbitrary tenant-supplied formula would necessarily *re-derive* something - combining columns, applying a caller-chosen aggregation - and that is exactly the class of second-source-of-truth risk §0 exists to prevent, applied here to a tenant's own formula rather than a platform gap. So the honest scope for "custom metric" in this platform is narrower than "custom formula" might imply, and this ADR makes that narrowing an explicit decision rather than something a future reader has to reverse-engineer from the registry's own code.

Two questions followed from this, once the scope was settled:

1. **What does "validate" mean if there's no formula to parse?** Structural validation (sourceView/valueColumn/dimensions match the whitelist) is necessary but was already enforced at *query* time by Phase 4's `MetricQueryEngineService`. §0.5 wants it enforced at *creation* time too, with a real dry-run against real data - catching a whitelist-passing-but-still-broken definition (e.g., a dimension name valid in the registry but somehow mismatched at runtime) before it is ever attached to a widget, not on that widget's first real page load.
2. **What does "cost-tier by measured dry-run latency" mean when every whitelisted source is a pre-computed, tenant-id-indexed rollup table?** Every one of the four `analytics_mv.mv_*` tables was built specifically so a bounded, indexed read is always cheap (§3's own design goal) - there is, by construction, no whitelist-legal query shape that is genuinely "expensive" today. The gate is still real and still worth building: it is what stops a *future* source view (added in a later phase, potentially without the same indexing discipline) from silently becoming "expensive" without anyone noticing, and it is measured, not asserted - this ADR does not hardcode "always cheap," it runs a real timed query and classifies from the result.

## Decision
**`MetricValidationService.validateAndTier`** is the one gate every tenant-authored `MetricDefinition` passes through at creation time (`createMetricDefinition`, this phase's own new mutation - §4.1 never named one, added here as a structurally necessary write path per the same "add what a described capability structurally requires" precedent as `saved_report.name`/`ComplianceReport.status`):

1. **Structural check**: `calculationDefinition.sourceView`/`valueColumn` must match `SOURCE_VIEW_REGISTRY`; any `dimensions` entries must be a subset of that view's `allowedDimensions`. Reuses the exact same registry `MetricQueryEngineService` already checks at query time - one whitelist, checked twice, never two whitelists that could drift apart.
2. **Dry-run**: one bounded, tenant-scoped, real query against the actual source table (`SELECT {valueColumn} FROM {table} WHERE tenant_id = ... ORDER BY period_start DESC LIMIT 5`, via `ANALYTICS_APP_REPLICA_PG_POOL`/`withTenantScopedClient` - the identical read path a live widget would use, at a smaller `LIMIT`) - a definition that is whitelist-legal but fails at runtime for any other reason is rejected here, not discovered on a dashboard's first real load.
3. **Cost-tiering by measured wall-clock duration** of that dry-run: `< 100ms` → `cheap`, `100–1000ms` → `moderate`, `> 1000ms` → `expensive`. Disclosed placeholder thresholds, not load-tested constants - Phase 8's own load test is this platform's first real opportunity to say whether these numbers are right; revisit then, the same "placeholder default, not a considered production value" posture this platform already applies elsewhere (e.g. `ADHERENCE_MAJOR_DEVIATION_THRESHOLD_SECONDS`).
4. **`validated_at`/`estimated_cost_tier` are set together, only on success.** A definition whose dry-run throws is rejected outright (`MetricValidationFailedError`) - never stored with `validated_at: NULL` for someone to accidentally use later, and never stored with a guessed tier.

**`createDashboard`'s existing widget guard is extended**: a widget may not reference a metric with `estimatedCostTier = 'expensive'` (Phase 4) **or `validatedAt IS NULL`** (this phase) - an unvalidated metric cannot back a live widget any more than an expensive one can, closing the gap Phase 4 left (its own guard only checked cost tier, since nothing before this phase could ever produce an unvalidated row).

**This module's six platform-default metrics (Phase 4) are not retroactively re-validated through this pipeline** - they were reviewed by this build's own migration, not dry-run-measured, and remain `estimated_cost_tier = 'cheap'` by direct assertion. This pipeline exists for rows this module did not author itself.

## Consequences
- A tenant can create their own named metric (e.g. `"night_shift_overtime"` → `mv_cost_vs_budget.overtime_hours`), but cannot invent a new computation - the exact scope this ADR commits to, stated in `createMetricDefinition`'s own resolver doc comment so a future reader doesn't have to infer it from the registry.
- Every dry-run-tiered metric in this platform today will measure `cheap`, by construction of the source tables - expected and correct, not evidence the gate does nothing. The gate's value is in what it *would* catch (a slow future source view, a whitelist-legal-but-broken definition) and in the mutation-time failure mode being immediate and typed, not a silent 500 on a widget's first real load.
- `analytics_metric_definition_validations_total{result, cost_tier}` (new metric, this phase) gives this pipeline the same "declared and wired from day one" observability posture every other phase's own new mechanism gets - watch for a real `expensive` or `error` outcome to know the moment this stops being purely theoretical.
- If a future source view genuinely needs a richer formula language than "column + dimension filter," that is new, separately-scoped work with its own ADR - not a reason to have built one speculatively now.
