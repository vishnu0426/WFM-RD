# ADR-0136: `integration_hub` is a new schema in the shared `agno_wfm` database, with its own runtime role

## Context
Same answer as ADR-0017/0052/0066/0073/0083/0093/0108/0113, for the same reasons. Module 12 needs its own durable Postgres presence for `IntegrationConnector`, `FieldMapping`, `SyncJob`, `WebhookSubscription`, `WebhookDelivery`, `ProviderRateLimitConfig`, and `FieldAuthorityPolicy` (§2.1). Nothing about this module's data volume argues for new infrastructure — `IntegrationConnector`/`FieldMapping`/`WebhookSubscription`/`FieldAuthorityPolicy` are low-cardinality admin-configured rows (one per tenant-provider pairing, not per-event), and while `SyncJob`/`WebhookDelivery` do accumulate history over time, neither is flagged in the module prompt as needing partitioning the way `core.audit_log` (ADR-0005) or Module 05's `adherence_event` (ADR-0066) were — this ADR does not add partitioning speculatively; see the Phase 1 design doc's explicit-assumptions section for what would change that.

This module's own non-negotiable (§0/§2.2 rule 3, restated in ADR-0135) is that it never writes to another module's operational tables directly — Module 02's bulk-import API, Module 06's leave/attendance APIs, and Module 05's `activity-events` endpoint are the only inbound write paths. That non-negotiable argues even more strongly than usual for this module owning its own isolated schema/role: `agno_integration_hub_app` must be structurally incapable of reading or writing `org.*`, `attendance_leave.*`, or `intraday.*` even if a future bug tried, since this module already holds the platform's largest external-credential attack surface (ADR-0134) — a schema-boundary mistake here would compound a credential-handling mistake, not just a data-isolation one.

## Decision
A new schema, `integration_hub`, owned by `agno_migrator` (DDL only), and a new runtime role, `agno_integration_hub_app`, with `USAGE` on `integration_hub` alone — not `core`, `org`, `attendance_leave`, `intraday`, or any other module's schema. `agno_integration_hub_app` gets per-table grants in the initial migration, and those grants are **not uniform across all seven tables** (see Consequences) — the first schema in this platform where the standard "SELECT/INSERT/UPDATE, no DELETE, on every table" template from ADR-0073/0083/0093/0113 doesn't apply unmodified to one of its own tables.

Cross-schema references are plain `uuid` columns (`FieldMapping.connector_id` → `IntegrationConnector.id`, etc., all within this same new schema) — no SQL `REFERENCES` reaches into another module's schema, matching ADR-0052/0073's established discipline. This module's actual cross-module dependencies (Module 02's bulk-import endpoint, Module 06's leave/attendance endpoints, Module 05's `activity-events` endpoint) are REST/gRPC contract calls, never table references, per §0/§2.2 rule 3.

## Consequences
- `scripts/init-roles.sql` gains `agno_integration_hub_app`, the `integration_hub` schema (authorized to `agno_migrator`), and the matching `GRANT CONNECT`/`GRANT USAGE`/`ALTER ROLE ... SET search_path` lines — additive only, no existing role or schema's grants change.
- **`ProviderRateLimitConfig` is the one table in this schema where `agno_integration_hub_app` gets `SELECT` only, no `INSERT`/`UPDATE`/`DELETE`.** Per `docs/module-12-provider-research.md`, this table holds platform-operator-maintained reference data (per-provider rate limits, researched against each vendor's actual published docs, several explicitly `unconfirmed`/`is_published: false`) — not tenant-configured data, and nothing in §3's API contracts exposes a mutation for it. It is seeded and updated by `agno_migrator`-run migrations (the same role/mechanism that seeds `core.permission`'s global rows, ADR-0002's carve-out precedent), not by the running application. If a future phase needs an admin-facing "override this provider's rate limit" mutation, that's a real scope addition requiring its own ADR and its own grant widening — not assumed here.
- The other six tables follow the established template: `SELECT, INSERT, UPDATE`, no `DELETE`, no `CREATE` on the schema. This module's domain has no hard-delete mutation in §3 (`triggerManualSync`, `createConnector`, `updateFieldMapping`, `createFieldAuthorityPolicy`, `createWebhookSubscription` are all create/update-shaped) — connector/subscription removal, if ever needed, is a status transition (`paused`/`disabled`), not a row deletion, consistent with every prior module's "cancellation is a status update, not a delete" convention (ADR-0073's own restatement of this).
- Module 12 talks to Module 02/05/06's data exclusively through their own contracts (§0/§2.2 rule 3) — never by reading `org.*`/`intraday.*`/`attendance_leave.*` tables directly, since the running role has no grant to do so.
