# ADR-0117: tenant-selectable, bring-your-own-key LLM provider (Anthropic + OpenAI) — a deliberate, explicit deviation from §1's "Anthropic only, platform-wide" default

## Context
§1's mandatory tech stack table states the LLM provider choice in absolute terms: "Anthropic API (Claude) ... **Explicitly NOT allowed**: Any other LLM provider as the default, per the source spec's explicit choice." Phase 2's first implementation followed this literally - a single `AnthropicMessagesClient`, model/key read from platform-wide env vars (`ANTHROPIC_MODEL`/`ANTHROPIC_API_KEY`), the only `LlmClient` registered in `AiModule`.

This was **explicitly overridden by the platform owner mid-build**, not discovered as a gap in the spec. Asked directly, two decisions were made:

1. Support both Anthropic and OpenAI, tenant-selectable (not a platform-wide default with tenants stuck on whichever one the platform's operators chose).
2. Bring-your-own-key (BYOK) - each tenant supplies and stores their own provider API key, not a platform-managed key/model tenants merely pick from a list. The platform never pays for or is billed for a tenant's own LLM usage under this model.

This ADR records that override explicitly, rather than letting it read as an accidental spec violation. §1's own text is unambiguous that this deviates from the source spec's stated intent - that is acknowledged here, not argued away.

## Decision
- **New entity, `AiProviderConfig`** (not in §2.1's literal list) - one row per tenant: `provider` (`anthropic` | `openai`), `model` (a bare string, never hardcoded/defaulted anywhere in code), and `encrypted_api_key`. Configured via `configureAiProvider` (GraphQL mutation, upserts) and never read back by any query - the same "write-only after creation" posture ADR-0046 established for `oauth_clients`' webhook signing secret.
- **Encryption at rest, not plaintext.** `AiProviderCredentialCipherService` - AES-256-GCM, random IV per encryption call, key from `AI_PROVIDER_CREDENTIAL_ENCRYPTION_KEY` (a static env var in this phase - real encryption, but key rotation/KMS-backed storage is a disclosed, not-yet-built production requirement, flagged loudly in the readiness checklist, not silently left implicit).
- **`LlmClient` stays the single provider-agnostic interface** it already was; the registered implementation becomes `ProviderRoutingLlmClient`, which takes a `ResolvedLlmProvider {provider, model, apiKey}` on every call and constructs a fresh, stateless provider SDK client (`@anthropic-ai/sdk` or `openai`) per call - never a long-lived client holding one tenant's key, since a second tenant's request on the same running instance must never be able to reach the first tenant's credentials.
- **No platform-paid fallback.** A tenant who hasn't called `configureAiProvider` yet has nothing configured - `AiProviderConfigService.resolveForCall` throws `AiProviderNotConfiguredError`, caught by every interaction-generating service (`ScheduleExplanationService` today) exactly where `LlmCallFailedError` already was, entering the same §4 degraded-mode path. "Not configured" and "provider temporarily down" are both, honestly, "no real LLM call happened this time" - a caller shouldn't need a different code path to get a non-crashing, structured-data-only response either way.
- **Both providers are real, live implementations from day one** - unlike ADR-0111's `NotAvailableNlQueryBridgeClient` precedent (a genuinely missing downstream service), an LLM provider is this module's own core competency; there is no "not available yet" stub for either branch of `ProviderRoutingLlmClient`.
- **§1's model-identifier discipline still holds, generalized across two providers**: nothing in this module hardcodes a specific Anthropic or OpenAI model id, context window, price, or rate limit. The model identifier always comes from the tenant's own `AiProviderConfig.model` value, verified by the tenant (or whoever configures it for them) against each provider's own current documentation - this module has no opinion on what a "current" model id is for either provider.

## Consequences
- `configureAiProvider`/`aiProviderConfig` are real, admin-intent GraphQL operations but are **not RBAC-gated** in this phase - no auth/RBAC guard exists anywhere in this service yet (the same header-trust `TenantContextMiddleware` placeholder every module's own Phase 1/2 starts with, ADR-0014). This is flagged more loudly than the usual "RBAC comes later" placeholder in the readiness checklist: the write in question is a secret credential, not ordinary domain data, and any tenant-authenticated caller can currently set or overwrite the tenant's own provider config.
- The `AI_PROVIDER_CREDENTIAL_ENCRYPTION_KEY` env var is a single static secret whose own compromise decrypts every tenant's stored key - a real production deployment needs this sourced from a KMS/secrets manager with rotation, not a static env var (the same "local-dev-appropriate, disclosed production gap" class as `changeme_local_only` passwords elsewhere in this platform, but higher-stakes since it protects other parties' third-party credentials, not just this platform's own).
- `AIInteraction.model_used` now carries a provider prefix (`anthropic:claude-...@schedule-explanation-v1` / `openai:gpt-...@schedule-explanation-v1`) - §0.5's "prompt/response versioning as a release-gated artifact" now also implicitly tracks provider, which is exactly the information a hallucination-rate regression investigation would need to know first (is this a prompt-version regression, or a provider-specific one).
- If a future phase wants a third tier - "platform-managed key, tenant just picks a model" (the option explicitly *not* chosen here) - that is a real, additive design decision (a new `AiProviderConfig` mode or a parallel table), not something this ADR's BYOK-only shape already accommodates.
