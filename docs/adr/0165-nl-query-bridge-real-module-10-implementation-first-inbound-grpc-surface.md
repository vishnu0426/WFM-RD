# ADR-0165: `askAnalyticsQuestion`'s NL bridge gets a real implementation — Module 10's first inbound gRPC surface, reversing its own "GraphQL only" boundary

## Context

ADR-0111 shipped `askAnalyticsQuestion` (analytics-reporting-service, Module 09) as a real, typed `NlQueryBridgeClient` contract with the only registered implementation (`NotAvailableNlQueryBridgeClient`) throwing unconditionally — Module 10 (ai-layer-service) did not exist anywhere in this platform at the time. It does now (Phases 2–9 built `explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis`/`askQuestion`, all GraphQL mutations with real BYOK LLM calls behind them). This phase closes ADR-0111's own gap: give `askAnalyticsQuestion` a real bridge to Module 10.

Every existing Module 10 integration has Module 10 as the **caller** — it gRPC-fetches context from Module 03/04/05/08's own servers, then makes the LLM call itself. `askAnalyticsQuestion` needs the opposite: Module 09 already has (or is about to execute) the data; it needs Module 10 to (a) translate a question into a structured query before execution and (b) turn results into prose after. Module 10's own `main.ts` said, verbatim, since Phase 1: *"No gRPC surface of its own is planned for this module (§1/§6 list GraphQL as the primary API surface, gRPC only as an outbound client to other modules)."* Honoring that literally would mean building this as a GraphQL-to-GraphQL service call — but no service-to-service auth capable of that exists: `client_credentials` tokens (core's OAuth server, Phase 2) carry no `roles`/`permissions` by design ("a client-level permission grant is not in scope for Phase 2"), so such a token could never pass `PermissionsGuard`, and are scoped to one fixed tenant per registered client, not arbitrary.

## Decision

Reverse the gRPC half of Module 10's boundary. `ai-layer-service` gets its first inbound gRPC surface, `NlQueryBridgeService` (`TranslateQuestion`/`GenerateAnswer`, `agno.ai_layer.v1`, port `7300`) — the same zero-auth, internal-network-trust model every other inter-service gRPC call in this platform already uses, not a new auth mechanism. `analytics-reporting-service` gets its first gRPC client of any kind (`AiLayerGrpcClientModule`/`AiLayerGrpcClientService`) to call it.

**Wire contract**: every response carries its own `error_code` (`""` on success, else `UNAVAILABLE`/`RATE_LIMITED`/`QUESTION_TOO_LONG`) rather than a thrown gRPC status — the same "return a typed outcome, don't throw across the wire" convention `ComplianceRuleGrpcController`'s `found: false` sentinel established. `GrpcNlQueryBridgeClient` (Module 09) maps these back into `NlQueryBridgeUnavailableError`/`NlQueryBridgeRateLimitedError`/`AnalyticsQuestionTooLongError`.

**`NlQueryBridgeClient` widened** beyond ADR-0111's original guess (the "revisit with its own ADR then, not now" it explicitly allowed for):
- `userId: string | null` added to both methods — threaded from the resolver's `@CurrentTokenClaims()` purely so Module 10's own `AiInteraction`/rate-limit attribution has a real actor, same as every other `AIInteraction`-generating operation.
- `availableMetricNames: string[]` added to `translateQuestion` — the tenant's real, visible metric catalog (`MetricDefinitionService.listVisibleMetrics`), the one grounding fact keeping translation from hallucinating a metric name Module 09 would just reject at query time.

**Module 10 side** (`NlAnalyticsBridgeService`): own copy of `ForecastExplanationService`/`AskQuestionService`'s pipeline (BYOK provider resolve → LLM call → parse → persist `AiInteraction` → audit), minus the "gather context via gRPC" step neither method needs (Module 09 already supplies everything inline). New prompt pair (`nl-analytics-bridge-prompt.ts`) — deliberately not a reuse of `askQuestion`'s own `NL_QUERY_SYSTEM_PROMPT` (scoped to "the one resource the caller identified," a different shape than a metric result series). `translateQuestion`'s own parser (`parseNlAnalyticsTranslation`) validates the model's `metricName` against the real `availableMetricNames` list server-side — a prompt instruction not to hallucinate is not a data-integrity guarantee. Neither method has a non-LLM fallback (same as `askQuestion`): a degraded attempt still persists its `AiInteraction` row (`degradedMode: true`), then returns `error_code: "UNAVAILABLE"` rather than a fabricated result. One new `AiInteractionType` (`analytics_nl_bridge`, migration `AiInteractionAnalyticsNlBridgeType`) covers both calls, distinguished by `input_context.step`.

**Rate limiting**: `NlAnalyticsBridgeService` calls `AiInteractionRateLimiterService.tryAcquire` directly (the same `(tenantId, actorId)` token bucket `AiInteractionRateLimitGuard` already enforces for every GraphQL-originated `AIInteraction` call) rather than through that Guard — a gRPC controller has no `CanActivate` pipeline. Same limiter instance (`AiModule` imports `AuthModule`), different enforcement point — a disclosed deviation, not a second, drifting implementation.

## Alternatives considered

1. **Route through core's OAuth `client_credentials` grant, GraphQL-to-GraphQL.** Rejected — that grant issues zero permissions/roles by Phase 2's own explicit design; making it usable here would mean redesigning core's own OAuth authorization model, a decision that belongs to whoever owns that subsystem, not a scoped fix to one NL-bridge gap.
2. **A new internal shared-secret REST endpoint on Module 10.** Would have worked, but invents a second, bespoke inter-service auth mechanism this platform doesn't otherwise have, for a boundary (internal service mesh) every other module already crosses with zero auth via gRPC. Rejected in favor of matching the existing, dominant pattern.
3. **Leave `askAnalyticsQuestion` unbuilt / keep `NotAvailableNlQueryBridgeClient`.** Was the honest Phase-7 answer when Module 10 genuinely didn't exist (ADR-0111). It does now — leaving the stub in place after building four other real Module 10 capabilities would no longer be an honest disclosure, it would be a known-stale one.

## Consequences

- `askAnalyticsQuestion` is fully wired end-to-end and live-verified (real OAuth token, real gRPC round trip, `MetricDefinitionService.listVisibleMetrics`'s real catalog observed in the persisted `AiInteraction.input_context`) — it still returns `NL_QUERY_BRIDGE_UNAVAILABLE` in this sandbox because no tenant has a configured `AiProviderConfig` (no real LLM API key available here), the identical, expected posture every other AI interaction in this platform already has in this environment.
- Module 10's own `main.ts`/`app.module.ts` doc comments no longer say "gRPC only as an outbound client" — updated in place to describe the reversal and why.
- `NotAvailableNlQueryBridgeClient` (and its spec) deleted — it asserted a fact ("Module 10 does not exist") that is no longer true; keeping it around unregistered would be dead, misleading code.
- Full regression suites re-run clean on both services after this change: ai-layer-service 209/209 (15 new), analytics-reporting-service 169/169 (19 new). `tsc -b`/`npm run lint` clean on both. All 11 HTTP services + the new gRPC surface verified healthy after a full `./dev.sh start`.
