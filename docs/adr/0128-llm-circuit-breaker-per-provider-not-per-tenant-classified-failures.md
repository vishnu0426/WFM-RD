# ADR-0128: the LLM circuit breaker is keyed by provider, not by tenant — and only classified, provider-side failures count toward opening it

## Context
§9 Phase 7 calls for "the full circuit breaker" for LLM outages - every phase since Phase 2 has run with a real but minimal degraded-mode posture instead: each interaction-generating service independently catches an `LlmCallFailedError`/`AiProviderNotConfiguredError` per call and falls back to §4's degraded-mode path. That per-call catch is real and correct, but it means a genuine provider-wide outage is discovered independently, the slow way (a real ~20s `CALL_TIMEOUT_MS` network attempt per call), by every tenant's every request, rather than detected once and then failed fast.

Two real design questions needed resolving before this could be built, not discovered mid-implementation:

1. **Keyed by what?** This module is multi-tenant, BYOK (docs/adr/0117) - each tenant supplies their own provider, model, and API key. A naive per-tenant circuit would mean 100 tenants each independently rediscover the same Anthropic outage; a naive fully-global circuit (one breaker for both providers) would incorrectly degrade OpenAI-configured tenants because Anthropic is down, or vice versa.
2. **What counts as a "failure" toward opening it?** A tenant's own revoked/invalid API key produces a real `LlmCallFailedError` (401/403) on every call, forever, until they fix it - if that counted the same as a genuine provider outage, one tenant's bad key would open a shared circuit and degrade every *other* tenant using the same provider, which would be a real, novel multi-tenant bug this ADR would be introducing, not fixing.

## Decision
- **Keyed by provider** (`anthropic` | `openai`), not by tenant and not fully global. `LlmCircuitBreakerService` holds independent state per `AiLlmProvider`. A real Anthropic-side outage opens only the Anthropic circuit; OpenAI-configured tenants are unaffected, and vice versa.
- **Failures are classified before they're recorded.** `ProviderRoutingLlmClient.isCountableFailure` treats HTTP 400/401/403/404/422 (bad request, auth, not-found, invalid model) as tenant-specific - these never call `LlmCircuitBreakerService.recordFailure` with a countable failure, so one tenant's bad key can never open the shared circuit. Every other failure shape - 5xx, 429, timeouts, network errors, and unexpected response shapes (e.g. the "no text content block" case, a genuine anomaly in an otherwise-200 response) - counts, since none of those have a plausible tenant-specific explanation.
- **State machine**: `closed` (every call attempted normally) → after 5 consecutive countable failures → `open` (every call short-circuited immediately, no network attempt, throws `LlmCallFailedError` the same as a real failure would) → after a 30s cooldown elapses → `half_open` (exactly one trial call let through; concurrent calls arriving while the trial is in flight are still short-circuited) → trial succeeds → `closed`; trial fails → back to `open`, cooldown restarted.
- **The short-circuit path reuses `LlmCallFailedError`** rather than introducing a new error type - every existing interaction-generating service's own degraded-mode `catch` block (`ScheduleExplanationService`, `ForecastExplanationService`, `ReallocationRationaleService`, `RootCauseAnalysisService`, `AskQuestionService`) needed zero code changes to benefit from the breaker.
- **In-memory, per-process only.** No shared/distributed state store exists for this (or any) service in this platform's current build - a real, disclosed limitation for a future multi-replica deployment, not something silently assumed away.
- **Drive-by fix**: `LlmCallFailedError`'s message previously hardcoded "Anthropic API call failed" regardless of which provider actually failed - a real, if minor, correctness bug predating BYOK's own introduction (docs/adr/0117) that became actually load-bearing here, since accurate per-provider attribution in logs/error messages matters once there are two independently-circuit-broken providers to tell apart. Fixed via an optional `provider` constructor parameter, defaulting to a generic `'LLM'` label so every pre-existing spec file's own direct `new LlmCallFailedError(new Error(...))` construction (used to simulate a failure at the interaction-service level, never through the real client) keeps compiling and passing unchanged.

## Consequences
- A real Anthropic outage now fails fast for every Anthropic-configured tenant after the first 5 consecutive real failures, instead of every subsequent call still paying the full ~20s timeout before falling back to degraded mode - a meaningful latency improvement for tenants during an actual outage, with no behavior change for tenants on the unaffected provider.
- `ai_llm_api_calls_total{result="short_circuited"}` is a new, distinct metric value from `result="error"` - reading a spike in `short_circuited` as "the breaker is protecting us" rather than "the provider is newly failing" is the correct interpretation, called out directly in `MetricsService`'s own doc comment.
- 17 new unit tests (9 for `LlmCircuitBreakerService`'s own state machine using Jest fake timers to control the cooldown deterministically, 8 for `ProviderRoutingLlmClient`'s integration of the gate + classification + real Anthropic/OpenAI SDK error shapes, the SDKs mocked for the first time in this module's test suite) - 97 total, up from 80, all passing.
- If a future multi-replica deployment needs the breaker's state to be consistent across instances, that's a real, separate piece of infrastructure (e.g. a shared Redis-backed state store) - not a redesign of the state machine itself, which stays the same regardless of where its state lives.
