# ADR-0123: `AIRecommendation` lifecycle — `suggest_only` never executes even when "approved"; `resolved_autonomy_level` stored in full, not just the derived boolean

## Context
§3's autonomy-level enum (`suggest_only | approve_required | auto_execute_low_risk`) resolves `requires_human_approval: true` for both of the first two levels - `AIGovernancePolicy`'s own schema (ADR-0113) never distinguished them further. But `decideRecommendation`'s actual behavior needs to: does an `'approved'` decision on a `suggest_only` recommendation call the owning module's write API, the same as an `'approved'` decision on an `approve_required` one?

The source spec doesn't say directly. The literal name "suggest only" is the strongest signal available: the AI's role for that `action_type` is to *suggest*, full stop - a human nodding along should not itself be what closes the loop. This is also the more conservative reading, consistent with `suggest_only` being strictly less permissive than `approve_required`, which is itself less permissive than `auto_execute_low_risk` - a three-level ordering where only the middle and top levels ever result in this module actually calling out to execute something.

## Decision
- `AiRecommendation.resolved_autonomy_level` (new column, additive migration) stores the full autonomy level resolved at creation - not just `requires_human_approval`. Necessary because `decideRecommendation` needs to tell `suggest_only` and `approve_required` apart at decision time, and nothing else on the row does.
- `AiRecommendationService.decideRecommendation`: a `'rejected'` decision never executes anything, for any autonomy level (obviously). A `'approved'` decision on `approve_required` calls the owning module's write API for real (§3/non-negotiable #1's governed pathway). A `'approved'` decision on `suggest_only` only updates `status`/`decided_by`/`decided_at` - purely advisory record-keeping, and any actual action has to happen through the owning module's own normal UI/API, entirely outside this pathway.
- `auto_execute_low_risk` never reaches `decideRecommendation` in the passing case - `createFromInteraction` evaluates risk thresholds immediately and executes right there, with `decided_by: null` (no human involved) and `status: auto_executed` set atomically with the execution call.

## Consequences
- A tenant configuring `suggest_only` for an `action_type` gets exactly what the name promises: recommendations appear, a supervisor can mark them approved/rejected for their own tracking, but Module 10 will never itself trigger the underlying action for that `action_type` - which also means `approve_required` is the *effective* minimum autonomy level for anything a tenant actually wants executed through this pathway.
- Backfilled as `approve_required` for any pre-existing row when the column was added (none existed in practice - `ai_recommendation` had no writer before this phase) - the safer of the two `requires_human_approval: true` levels to assume retroactively, never `auto_execute_low_risk`.
- **Live-verified for real** (not just mocked): a genuine `AiRecommendationService.createFromInteraction` → `decideRecommendation('approved')` round trip against a real, running intraday-service correctly flipped the underlying `reallocation_action` row to `executed` via a real HTTP call - see ADR-0124. The `suggest_only` advisory-only branch is unit-tested (mocked) but was not exercised in that live pass, since it has, by design, nothing external to call.
