# ADR-0127: `askQuestion` requires a caller-supplied resource pointer — no NL entity-resolution capability is built, and there is no degraded-mode fallback for a failed LLM call

## Context
§9 Phase 6 describes `askQuestion` as "NL query / conversational interface," which reads, on a literal interpretation, as free-text in, free-text out with no other required input - implying the platform can figure out on its own which schedule, forecast, reallocation, or org unit/period a question is "about." No such capability exists anywhere in this platform. ADR-0111 already disclosed the identical gap for Module 09's `NlQueryBridgeClient` ("real contract not implemented" - a `NotAvailableNlQueryBridgeClient` stub is the only implementation, by design). Building real entity resolution here - parsing "why was Maria's shift moved last week" into `reallocationActionId: "..."` - would mean either a second LLM call whose own output silently becomes a lookup key (a channel non-negotiable #2 was written to prevent: the LLM would be inventing which real-world record a phrase refers to, not just describing one already handed to it) or a bespoke NL-to-SQL/search layer that is a substantial system in its own right and was not asked for.

A second, separate question: what happens when the LLM call itself fails? Every existing interaction type (`explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis`) has a real non-LLM fallback under §4 - the raw structured data it already retrieved, returned with `degraded_mode: true`. An NL query's raw grounding data is not, itself, an answer to the question that was asked - returning it under the guise of "degraded but still a response" would not honor non-negotiable #2 any better than fabricating one.

## Decision
- **`askQuestion(question: String!, context: AskQuestionContextInput!)`** requires the caller to identify exactly one of four existing resources: `scheduleJobId`, `forecastRunId`, `reallocationActionId`, or `orgUnitId` + `periodStart` + `periodEnd` together. `AskQuestionService.resolveSource` enforces "exactly one" as an explicit runtime check (`AskQuestionContextInvalidError`, mapped to 400) - not a GraphQL-schema-level `oneOf` union, since no such construct exists in GraphQL's own type system without significant added complexity for four optional scalar fields.
- Whichever source is identified, `AskQuestionService` calls that resource's own `gatherContext` method (docs/adr/0126) - the exact same real data `explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis` already ground their own answers in, never a fifth, NL-query-specific fetch path.
- The free-text `question` is answered strictly against that one resource's grounding data (`nl-query-prompt.ts`'s system prompt states this explicitly, in terms of two labeled blocks: `GROUNDING DATA` and `USER QUESTION`) - §5.2's untrusted-content handling applies to the entire `question` field, not just a sub-field the way it did for `ReallocationRationaleService`'s `reason` (Phase 4, the first real exercise of that boundary).
- **No raw-data fallback on LLM failure.** When the LLM call fails (`LlmCallFailedError`/`AiProviderNotConfiguredError`), `AskQuestionService` still persists a real `AiInteraction` row (`degradedMode: true`, `outputText: null`, `outputStructured: null`) - the attempt happened and is auditable, the same invariant every other interaction type keeps - but then throws `AiAssistantUnavailableError` to the caller, whose message is the exact UI copy §9 Phase 6 specifies: "AI assistant is temporarily unavailable — try the dashboard directly." A caller that wants the raw grounding data instead already has a real path to it: `explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis` directly, whichever matches.
- **Human-in-the-loop is structural, not an added check.** `AiRecommendationService.createFromInteraction` (Phase 5, docs/adr/0123) only ever accepts an interaction whose `interactionType` is `reallocation_rationale`; `askQuestion` always produces an `nl_query`-typed interaction. An `nl_query` interaction can never seed an `AIRecommendation`, so `askQuestion` cannot auto-trigger an action even in principle - proved directly in `ask-question.service.spec.ts` by feeding a real `askQuestion`-produced interaction id into `AiRecommendationService.createFromInteraction` and asserting `AiInteractionNotRecommendableError`. The system prompt's own "never present your answer as if the corresponding action has already happened" instruction is this design's concrete language-level reinforcement of the same guarantee, not a substitute for it.
- Kept as a GraphQL `Query`, matching `explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis` - all four also persist a new `AIInteraction` row despite being read operations from the caller's own point of view; only operations that mutate a pre-existing resource (`createReallocationRecommendation`, `decideRecommendation`, `updateGovernancePolicy`, `configureAiProvider`) are `Mutation`s in this module.

## Consequences
- If a real NL-entity-resolution capability is built later (for this module or for Module 09's own `NlQueryBridgeClient` gap), `askQuestion`'s `context` argument becomes optional-with-a-fallback-resolver rather than a redesign - the required-pointer path stays as the precise, no-guessing option; entity resolution stays a separate stage, not folded into this service's own LLM call.
- Callers get an honest 400 (`ASK_QUESTION_CONTEXT_INVALID`) for an ambiguous or missing pointer, rather than a guess. This is a real UX cost relative to a "just ask anything" NL assistant - disclosed here and in the Phase 6 readiness checklist, not softened.
- 8 new unit tests in `ask-question.service.spec.ts` (source-validation rejection paths, successful routing to each of the four `gatherContext` methods, the no-fallback-on-failure behavior, and the human-in-the-loop proof) plus all 72 pre-existing tests, 80 total, passing; `npm run build` and a schema inspection (`askQuestion(context: AskQuestionContextInput!, question: String!): AIInteraction!`) both confirmed after wiring.
