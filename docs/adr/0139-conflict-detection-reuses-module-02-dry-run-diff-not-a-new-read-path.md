# ADR-0139: Field authority conflict detection reuses Module 02's own bulk-import dry-run diff — no new read endpoint into Module 02

## Context
§5b's conflict detection needs to compare an incoming external value against Agno WFM's own *current* stored value for a field, for every field a tenant has marked `authoritative_source: agno_wfm`. The naive way to get "Agno's current value" is a new read call into Module 02 (e.g. "get employee by employee number"). Investigating this while building Phase 4 found two real facts that decided the design:

1. **No such read endpoint exists.** Module 02's own GraphQL only exposes `employee(id: ID)` (internal UUID, not the `employeeNumber` this module works with) with no `employeeNumber` filter anywhere in its `EmployeeFilterInput`. Building one would be new scope inside Module 02, out of this module's own boundary (§0/§2.2 rule 3: this module calls Module 02's *existing* governed APIs, never invents a shortcut — and "invent a new Module 02 read endpoint just for Module 12" is exactly the kind of shortcut that rule is written against).
2. **Module 02's bulk-import dry-run already computes almost exactly this diff.** `BulkImportService`'s own diff logic (`bulk-import-diff.ts`) returns, for every field it updates, `{ old: <current Agno value>, new: <incoming value> }` — keyed by field name, on every `result.updates[]` entry a dry-run produces. This is the *same* dry-run §2.2 rule 3a already requires this module to run before every commit.

## Decision
`detectFieldAuthorityConflicts` (`src/sync/batch/conflict-detection.ts`) takes the dry-run's own `BulkImportJobResult` as its input, not a separate read call. For each `FieldAuthorityPolicy` with `authoritative_source: agno_wfm`, it checks whether that field name appears in `result.updates[].changes` — if so, `changes[field].old` *is* Agno's current value and `changes[field].new` *is* the incoming value, exactly what §5b's detection rule needs, with zero additional Module 02 round trips.

**Consequence of this choice, not a limitation of the idea**: whatever fields Module 02's own diff logic does *not* cover, this module structurally cannot detect a conflict on either — most notably `hireDate`, which `bulk-import-diff.ts`'s own doc comment excludes by design ("an HRIS re-sending an employee's original hire date shouldn't be treated as a change worth reporting"). `userId` is excluded the same way. This is a real, disclosed gap: a tenant that configures `hire_date` as `agno_wfm`-authoritative (contrary to §5b's own suggested default of `external_system` for that field) would get **silent non-detection**, not a loud rejection - the field's real value would simply always flow through from the incoming record with no conflict ever flagged, since this module has no visibility into whether it changed at all. `FieldAuthorityPoliciesService` does not currently reject creating a policy on `hireDate`/`userId` specifically - a real, narrower gap than the general one this ADR is about, worth closing in a later phase (either reject policies on diff-excluded fields outright, or build the missing read path) rather than assumed away here.

**Only `updates` are compared, never `creates`.** A brand-new employee has no existing Agno value to conflict with by construction - `detectFieldAuthorityConflicts` correctly produces zero conflicts for anything in `result.creates`.

## Consequences
- Zero new HTTP calls into Module 02 beyond what Phase 3 already made (one dry-run, one commit) - conflict detection is free in terms of Module 02 round trips, at the cost of being scoped to exactly the fields Module 02's own diff already covers: `orgUnitId`, `employmentType`, `contractHoursPerWeek`, `costCenter`, `managerEmployeeId`.
- If a future need arises to detect conflicts on `hireDate`/`userId` (or any field a future Module 02 write path doesn't diff), the fix belongs in one of two places: Module 02's own `bulk-import-diff.ts` (if that team decides re-reported hire-date changes are actually valuable, which their own doc comment currently argues against), or a genuinely new, deliberately-designed read path into Module 02 - not a workaround invented unilaterally inside Module 12.
- `WorkdayAdapter`'s own conflict handling (`flag_for_review` reverts a field to `changes[field].old` before commit, `reject_sync` drops the whole record) depends on this same `{old, new}` shape being accurate - verified live against Module 02's real diff output, not assumed from reading its source (`docs/module-12-phase-4-design-doc.md`).
