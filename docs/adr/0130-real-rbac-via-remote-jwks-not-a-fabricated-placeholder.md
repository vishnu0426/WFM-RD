# ADR-0130: `configureAiProvider`/`updateGovernancePolicy` are RBAC-gated via a remote-JWKS copy of core's real, already-implemented guards — not a fabricated placeholder

## Context
Every readiness checklist since Phase 5 has flagged the same gap with escalating urgency: `updateGovernancePolicy` and `configureAiProvider` are unprotected by RBAC, unlike every other tenant-context-trust placeholder in this platform (ADR-0014) - because these two specifically control autonomy-level/auto-execution settings and BYOK credentials, not ordinary domain data. Closing this required first establishing what RBAC mechanism actually exists in this platform, rather than inventing one from scratch for this module alone.

It turns out real, non-placeholder RBAC already exists - not at ai-layer-service's own level, but in the root platform-core service (`src/modules/auth/rest/`): `AccessTokenGuard` (Bearer-token verification via `TokenService.verifyAccessToken`), `PermissionsGuard` + `@RequirePermissions(...)` (checks a flat `["resource:action", ...]` claim, ADR-0035's RBAC/ABAC split), and a real OIDC issuer (`TokenService`, `SigningKeyService`, `WellKnownController` serving `/.well-known/jwks.json`). ai-layer-service is a genuinely separate deployable service, with its own Postgres role/schema (ADR-0113) and no access to core's `signing_keys`/`permission`/`role` tables - it cannot simply import core's TypeScript modules. Two real design questions followed: how does a separate service verify a token it didn't issue, and how does a permission string become a real, grantable thing rather than an opaque string nobody can ever hold?

## Decision
- **`AccessTokenGuard`, `PermissionsGuard`, `@RequirePermissions`** are own copies of core's real guards (not new inventions), adapted for a remote resource-server role: `jose`'s `createRemoteJWKSet` fetches and caches core's public JWKS over HTTP (`CORE_JWKS_URI`, real OIDC Discovery) instead of core's own direct DB read (`SigningKeyService.resolveVerificationKey`) - the standard "resource server" half of the same OIDC architecture core implements as the "authorization server" half. `iss`/`aud` validation uses `OIDC_ISSUER`/`OIDC_AUDIENCE`, which must match core's own configured values exactly.
- **No revocation check** - core's own guard also calls `TokenRevocationService.isRevoked`, a live check against a store this service has no access to. Disclosed, bounded: access tokens are short-lived (`ACCESS_TOKEN_TTL_SECONDS = 720`), the standard trade-off most OIDC resource servers make instead of requiring a shared revocation cache with every downstream service.
- **`ai_provider_config`/`ai_governance_policy` are registered as real resources** in core's own `run-seed.ts` `RESOURCES` array - the one place a new resource needs registering (per that file's own comment) - so `ai_provider_config:write`/`ai_governance_policy:write` are real, seeded permissions, automatically granted to `platform_admin` and `tenant_admin` (every non-`tenant:delete` permission), not merely strings this module's guard happens to check with nothing on the other end able to hold them.
- **A new problem this cross-service split introduces, and its fix**: `PermissionsGuard` alone only proves the caller holds a permission *somewhere*, never that the token's own `tenant_id` claim matches the `x-tenant-id` header this service's tenant scoping actually runs on (ADR-0014's own placeholder). `CurrentTokenClaims` (a param decorator, not present in core's own copy - core doesn't need it, since its own guards and tenant resolution share the same request) feeds `assertTokenTenantMatches`, called explicitly in both gated resolvers, closing what would otherwise be a real hole: a valid token for tenant A holding the right permission, replayed against a spoofed `x-tenant-id: B` header.
- **A real, incidental improvement**: `updatedBy`/prior phases' own disclosed `null` placeholder ("no Module 01 IdentityService.GetUserContext gRPC call is wired into this phase") is resolved for these two mutations specifically - the verified JWT's own `sub` claim is a real authenticated identity, no gRPC call needed.
- **Scope, deliberately not expanded**: only these two mutations are gated. `decideRecommendation`, `pendingRecommendations`, `askQuestion`, and the four explanation queries remain on the header-trust placeholder (ADR-0014) - not because they're unimportant, but because they were never the specific, escalating disclosure these two mutations were. Expanding RBAC further is a separate, explicit scope decision for a future phase, not silently bundled into this one.

## Consequences
- Live-verified end to end, not just unit-tested: a real local HTTP server serving a real JWKS (a freshly generated RSA keypair, `jose.exportJWK`), real signed JWTs (`jose.SignJWT`) for three scenarios (valid token + correct permission + matching tenant → success with a real DB write and real `updated_by`; valid token missing the permission → 403 naming the exact missing permission; valid token for the wrong tenant against a spoofed header → 403 from `assertTokenTenantMatches`) - all three produced exactly the expected GraphQL error/success shape against a running `node dist/src/main.js` instance and the real Postgres database used throughout this module's build.
- 14 new unit tests (6 for `AccessTokenGuard` against a real, ephemeral JWKS HTTP server - not mocked - covering valid/missing-header/forged-key/expired/wrong-issuer/wrong-audience; 5 for `PermissionsGuard`; 3 for `assertTokenTenantMatches`) - 156 total, alongside this same phase's 30 prompt-injection tests (ADR-0131).
- A newly-introduced, disclosed observability gap (Phase 8 readiness checklist/dashboard): NestJS Guards run *before* `HttpMetricsInterceptor` in the request lifecycle, so a 401/403 from either new guard is invisible to every existing HTTP/GraphQL metric - there is currently no counter anywhere for RBAC denials.
- If RBAC needs to expand to more operations later, the pattern established here (own-copy guards + `CurrentTokenClaims`/`assertTokenTenantMatches` for the tenant cross-check + registering the resource in core's seed) is the template - not a redesign per additional gated mutation.
