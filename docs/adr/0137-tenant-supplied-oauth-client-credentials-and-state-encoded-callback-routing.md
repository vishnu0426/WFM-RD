# ADR-0137: Tenant-supplied OAuth client credentials, and encoding `tenantId`/`connectorId` into `state` for a header-less provider callback

## Context
§1 says OAuth-capable connectors use "standard OAuth 2.1 authorization code flow... reusing the same token-handling discipline (rotation, secure storage via Vault) as Module 01's own OAuth implementation," and §3.2 names `POST /v1/integrations/oauth/callback` as the completion endpoint. Two real design questions the module prompt leaves open surfaced while building Phase 2's connector-creation and callback code paths:

1. **Whose OAuth client (`client_id`/`client_secret`) is this?** Module 12 doesn't own a pre-registered developer app with any of the 10 named providers — in real enterprise SaaS integration, a tenant registers their *own* OAuth app/Connected App in their Workday/Salesforce/Genesys org and hands Agno the resulting `client_id`/`client_secret`, not the other way around. Module 01's own OAuth code (`src/modules/auth/`) is an authorization *server* issuing tokens to clients, not a client of external providers — a different direction entirely, with nothing to reuse directly here beyond the general discipline §1 asks for.
2. **How does a callback find its connector without a tenant header?** A provider's own redirect (the browser landing back on Agno after the tenant admin authorizes) carries no `X-Tenant-Id` header or session — `POST /v1/integrations/oauth/callback` is called by Agno's own frontend after it intercepts that redirect (an authenticated call, per §3.2 specifying `POST`, not the provider's raw `GET` redirect), but the frontend still needs to know *which pending connector* the `code`/`state` it just received belongs to, without a second round trip.

## Decision
**Each connector's OAuth client credentials are tenant-supplied, entered once at `createConnector` time**, identically to how the non-OAuth path already takes admin-entered credentials (§1). `clientSecret` follows the exact same Vault-reference discipline as any other credential (ADR-0134) — written to Vault immediately (`integration-hub/{tenantId}/{connectorId}/oauth-client-secret`), never persisted to `config`. `clientId`, the two endpoint URLs, and the redirect URI are not secret and stay in `config` directly (they're needed to build the authorization URL and re-run the token exchange on every future refresh).

**`state` encodes `tenantId.connectorId.nonce`.** The `nonce` (24 random bytes, hex) is what actually authenticates the callback — stored verbatim in `config.oauthState` at creation time, compared for exact equality in `completeOAuthCallback`, one-time-use (cleared once consumed). `tenantId`/`connectorId` let the callback recover which pending connector this belongs to directly from `state` itself, without a second lookup or a client-supplied `connectorId` argument that would have to be trusted. `tenantId`'s embedded value is cross-checked against the authenticated caller's own tenant context as defense in depth: a `state` string stolen from a different tenant's admin session is rejected before ever reaching the nonce comparison.

## Consequences
- A connector's OAuth registration is a per-connector, per-tenant artifact — two tenants integrating the same provider (or one tenant with two connectors to the same provider) each supply their own `client_id`/`client_secret`, matching how real Connected Apps/OAuth apps actually work in Workday/Salesforce/Genesys/etc. This module never needs (and never holds) a single shared platform-wide OAuth app credential for any of the 10 named providers.
- `state`'s three-part `tenantId.connectorId.nonce` shape is dot-segmented and can coincidentally match a generic "three base64url-ish segments separated by dots" pattern (i.e., look JWT-shaped) — the credential-shape guard (ADR-0134) exempts the `oauthState` field name specifically from its heuristics for this reason, found live when the guard rejected a real, correctly-generated state token during this phase's own end-to-end verification.
- A future token refresh (not built this phase) reuses `config.oauthClientSecretReference`/`oauthTokenEndpoint`/`oauthClientId` exactly as stored — this is why the client secret reference is kept after a successful callback while `oauthState` (one-time-use) is discarded.
- This module still has no real, credentialed developer relationship with any of the 10 named providers in this environment — Phase 2's own verification therefore exercised this entire flow (`createConnector` → authorization URL → callback → token exchange → Vault write) against a real, generic local OAuth 2.0 token endpoint standing in for "whichever provider a tenant actually registers," not against Workday/Salesforce/Genesys specifically. The exchange logic itself is provider-agnostic RFC 6749 §4.1.3, so this is the same code path a real provider's token endpoint would exercise — see `docs/module-12-phase-2-design-doc.md` for the verification transcript.
