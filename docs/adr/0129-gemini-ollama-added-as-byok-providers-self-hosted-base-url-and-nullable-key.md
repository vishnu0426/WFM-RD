# ADR-0129: Gemini and Ollama added as BYOK providers — a self-hosted provider needs a `baseUrl`, not just a key

## Context
Docs/adr/0117 established BYOK with two cloud providers (`anthropic`/`openai`), each with the same shape: tenant supplies a model name and an API key, this module resolves and decrypts it fresh per call. A request to add Gemini and Ollama surfaced a real difference between the two: Gemini is a third cloud provider with the identical shape to the existing two, but Ollama is normally **self-hosted** - a tenant's own instance, typically unauthenticated, with no fixed platform endpoint the way `api.anthropic.com`/`api.openai.com`/Gemini's API host are fixed. `AiProviderConfig`'s existing schema (`provider`, `model`, `encrypted_api_key NOT NULL`) had no field for "which address" and assumed every provider always has a real key - both assumptions had to change, not just the provider enum.

Two real questions needed resolving before writing code:
1. **How does a tenant tell this service where their Ollama instance is?** Resolved: a new `baseUrl` column, required specifically for `ollama`, unused by the three cloud providers.
2. **Does Ollama need an API key at all?** Most self-hosted Ollama deployments are unauthenticated; forcing a fabricated key would violate this module's own "never fabricate" convention. Resolved: `encrypted_api_key` becomes nullable - required for the three cloud providers (enforced in `AiProviderConfigService.configure`, not a NOT NULL column), optional for `ollama` (if supplied, sent as a Bearer header, since some self-hosted instances do sit behind an auth proxy).

## Decision
- **`AiLlmProvider` gains `GEMINI` and `OLLAMA`.** `AiProviderConfig.encryptedApiKey` becomes nullable; a new nullable `baseUrl` column is added (additive migration, `ai_provider_config_provider_check` CHECK constraint extended to all four values).
- **Validation lives in `AiProviderConfigService.configure`, not the GraphQL schema**: `ollama` requires `baseUrl`; every other provider requires `apiKey`. A GraphQL-level `!` can't express "required depending on a sibling argument's value" across four provider choices, so both `apiKey` and `baseUrl` are optional at the schema level (`AiProviderConfigInvalidError`, 400, is the real enforcement point) - the same "per-field decorators, cross-field rules in the domain service" split this module already uses elsewhere (`AskQuestionContextInput`, docs/adr/0127).
- **This platform never validates or tunnels to a tenant's self-hosted Ollama instance.** Reachability (is `baseUrl` actually reachable from this backend's network?) is entirely the tenant's own responsibility, disclosed explicitly here and in the readiness checklist - a materially different trust/network model than calling a public cloud API with a bearer token, and one this ADR does not attempt to close.
- **SDKs**: `@google/genai` (Google's actively maintained client - the older `@google/generative-ai` package has had no release since April 2025 and was not chosen) for Gemini; `ollama` (the official JS client) for Ollama. Both integrate into `ProviderRoutingLlmClient` behind the same `LlmClient.complete` interface, gated by the same `LlmCircuitBreakerService` (docs/adr/0128) as the two existing providers - each provider's own circuit state is fully independent, so a Gemini or Ollama outage never affects Anthropic/OpenAI-configured tenants or each other.
- **Failure classification extended, not redesigned**: `extractStatus` now also recognizes `@google/genai`'s own `ApiError.status` and duck-types Ollama's `status_code` field (the client library's `ResponseError` class isn't exported, only its `ErrorResponse` shape is - `instanceof` isn't available, so the one distinguishing field is checked directly). The existing tenant-specific-vs-provider-side split (docs/adr/0128) applies unchanged to both new providers.
- **Ollama has no built-in per-call timeout** in its own client library - `ProviderRoutingLlmClient.completeWithOllama` wraps the call in a `Promise.race` against a local timer at the same `CALL_TIMEOUT_MS` every other provider already respects, throwing a local `OllamaCallTimeoutError` classified as a real (`408`-equivalent) failure, not a different code path.
- **A real, if narrow, defensive check**: `completeWithOllama` throws immediately if `baseUrl` is missing, rather than trusting `configure`'s own validation silently - `new Ollama({ host: undefined })` falls back to the client library's own `localhost:11434` default instead of failing loudly, which would be a genuinely dangerous wrong-target failure mode for a multi-tenant service (silently trying to reach a different tenant's - or this service's own host's - local Ollama instance). `requireApiKey`'s equivalent check for the three cloud providers is comparatively lower-stakes (a missing key just fails immediately at the SDK constructor), but both exist for the same reason: catching an invariant violation at the one real boundary between configure-time validation and call-time consumption.

## Consequences
- `configureAiProvider(provider, model, apiKey, baseUrl)` - both credential arguments are now optional at the schema level; existing Anthropic/OpenAI callers are unaffected (still required in practice, enforced one layer down).
- `AiProviderConfigSummaryResult.baseUrl` is a new, non-secret field (unlike the key, safe to echo back) - `null` for every provider except `ollama`.
- A tenant switching from `ollama` back to a cloud provider (or vice versa) correctly clears the field that no longer applies (`baseUrl: null` when leaving `ollama`, `encryptedApiKey: null` when arriving at `ollama` with no key supplied) - proven directly in `ai-provider-config.service.spec.ts`.
- 23 new unit tests (9 for `AiProviderConfigService`'s validation/persistence rules, 6 for `ProviderRoutingLlmClient`'s Gemini/Ollama integration including the unexported-error-class duck-typing and the manual-timeout race) - 112 total, up from 97, all passing. Live-verified: a real migration run against the same running Postgres instance used since Phase 1, a full app re-boot, `src/schema.gql` inspected directly, and four live GraphQL calls (Ollama missing `baseUrl` → rejected; Ollama with `baseUrl` and no key → accepted; Gemini missing `apiKey` → rejected; Gemini with a key → accepted, read back via `aiProviderConfig`).
- No live call to a real Gemini API or a real Ollama instance was made in this session (same disclosed posture as every prior phase's "no live LLM call was made") - both providers' request/response handling is proven via mocked SDKs, not a live integration.
