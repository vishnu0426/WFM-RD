# ADR-0134: Integration connector credentials — Vault-reference discipline for both OAuth and non-OAuth providers

## Context
Module 12 (Integration Hub) holds references to the platform's largest external-attack-surface concentration: every tenant's HRIS, payroll, ACD, and CRM credentials. §1/§2.2 rule 1 require that `IntegrationConnector.config` (and `WebhookSubscription.secret_reference`) hold only a Vault reference key, never a credential value, with the same discipline Module 01 applies to identity secrets. The provider research in `docs/module-12-provider-research.md` surfaced that this module's providers do not share one credential shape: Workday, SAP SuccessFactors, ADP, Salesforce, the cloud ACD providers, and Avaya Experience Platform all support OAuth 2.0 (with real per-provider differences in grant type — Genesys and Talkdesk document Client Credentials as the server-to-server norm, NICE CXone's documented server-to-server pattern is Resource Owner Password Grant instead, and ADP requires mutual TLS *in addition to* its OAuth bearer token). Avaya Aura Contact Center / CMS has no OAuth flow at all — it authenticates via CMS Supervisor/Informix DB credentials or a TSAPI/AES CTI user account, both pre-OAuth credential shapes with no token endpoint to callback into. A design that assumes every connector eventually produces an OAuth token would leave the CMS/TSAPI path with no home, or worse, tempt a workaround that holds those credentials somewhere other than Vault "just for this one provider."

## Decisions
**Two credential-intake paths converge on one storage discipline.** `POST /v1/integrations/oauth/callback` handles every OAuth-capable provider — the callback receives the authorization code, exchanges it for tokens server-side, and writes the resulting access/refresh token pair to Vault immediately, returning only the Vault key to `IntegrationConnector.config.credential_reference`. The non-OAuth path (§1's "required addition, not in v1") runs through `createConnector` directly: the admin enters CMS Supervisor/TSAPI credentials (or ADP's client cert material, which is credential-shaped even though ADP *also* does OAuth — the cert is a second credential Vault must hold alongside the bearer-token reference) in the same mutation flow, and the resolver writes to Vault before the mutation returns, never persisting the raw value to any application table even transiently. Both paths produce the identical `IntegrationConnector.config` shape: a reference key and nothing else. The two paths differ only in *how* the credential material is obtained (three-legged redirect vs. a direct admin-entered field) — not in what happens to it once obtained.

**Multi-credential providers get multiple reference keys, not one.** ADP's mutual-TLS requirement means a single ADP connector's `config` holds two Vault references — one for the OAuth bearer-token material, one for the client certificate/key pair — rather than conflating them into a single reference or, worse, storing the cert outside Vault because "it's not really a credential, it's a cert." The write-path validation in rule 1 (reject any payload that looks like a raw credential) checks every credential-shaped field in the payload, not just a single assumed `token` field, so a connector-specific adapter can declare which fields need Vault-backing without the platform-level guard needing per-provider special-casing.

**The write-path validation check is provider-agnostic pattern matching, not a provider allowlist.** It rejects payloads matching common credential shapes (bearer tokens, API key patterns, base64-looking blobs above a length threshold, PEM-formatted key/cert material) regardless of `connector_type` or `provider` — this is what makes the non-OAuth Avaya path get the identical protection as the OAuth-based providers without a separate rule.

**No caching beyond the single operation's lifetime.** A batch sync job or a streaming relay's connection-establishment reads the credential from Vault once per operation and holds it only in memory for that operation's duration — a sync job doesn't cache a decrypted token across its scheduled runs, and a relay reconnect re-reads from Vault rather than reusing a token held from a previous connection window, closing the same gap the chaos-test in §0.5 is designed to catch (kill Vault mid-sync, verify fail-closed rather than fallback-to-cached).

## Consequences
- The connector-framework's Vault client needs exactly one write path and one read path, used identically by both credential-intake mutations — the OAuth callback and `createConnector`'s non-OAuth branch differ only in what triggers the write, not in how the write happens.
- Provider adapters (built per-provider in Phases 3 and 6) declare their own credential field shape (e.g. Avaya AXP: OAuth token; Avaya Aura/CMS: DB credentials + optional TSAPI client cert; ADP: OAuth token + mTLS cert) against this one framework, rather than each adapter inventing its own storage discipline.
- This ADR does not resolve IP-allowlisting for Avaya Aura/AES, which `docs/module-12-provider-research.md` flags as unconfirmed in public Avaya docs — if AES requires an allowlisted source IP, that's a network/infra decision (which egress IP this module's relay worker presents), not a credential-storage decision, and is out of scope here.
- Real test to add per §6: a single parameterized test asserting the write-path rejection fires for both a raw OAuth bearer-token-shaped payload and a raw CMS/TSAPI-credential-shaped payload, proving the guard isn't accidentally OAuth-specific.
