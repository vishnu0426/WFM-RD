# ADR-0121: `AdherenceRollupService` — adherence-compliance-service's second gRPC surface, an org-unit adherence aggregate for root-cause analysis

## Context
`rootCauseAnalysis`'s adherence data source needs an org-unit-level adherence summary for a period. `AdherenceScore` (Module 08, ADR-0098) is per-employee, per-period - the only place in this platform that already aggregates it by org unit is `ComplianceReportService.buildAdherenceSummary` (the `adherence_summary` CSV report's own roster-then-`AdherenceScore` join), and that's a per-employee/period CSV dump, not a summary, and not exposed over gRPC at all.

## Decision
`AdherenceRollupService.GetOrgUnitAdherenceSummary(tenantId, orgUnitId, periodStart, periodEnd)` - `adherence-compliance-service`'s second gRPC surface, same process/port/package (`agno.compliance.v1`) as the existing `ComplianceRuleService`. Reuses `buildAdherenceSummary`'s exact roster-then-`AdherenceScore` join (`EmployeeGrpcClientService.getSchedulableRoster` + a tenant-scoped `AdherenceScore` query), but returns an aggregate (`averageAdherencePct`, `totalMajorDeviationCount`, `minAdherencePct`/`maxAdherencePct`, employee/period counts) instead of one row per employee/period - a root-cause narrative needs "how bad, and how consistently," not a full ledger.

`found: false` when the roster is empty OR has zero `AdherenceScore` rows in the window - both are real "nothing to summarize" outcomes, not fabricated as a zero average. The response echoes `tenant_id` from a scored row itself (not merely the request's own field) for the same §5.1 defense-in-depth reason ADR-0115 already established - RLS already guarantees every row belongs to the caller's tenant, but the response shouldn't hand back the caller's own unverified input as if it were an independently-sourced fact.

## Consequences
- No new gRPC transport/registration mechanics needed - `main.ts`'s existing `connectMicroservice` call already loads the whole `compliance.proto` file, so adding a second `service` block to that same file and a second `@GrpcMethod`-decorated controller (registered via the same `GrpcModule`) required no changes to `main.ts` beyond the log line.
- **Verified**: 189/189 pre-existing unit tests still pass; 6 new tests cover the aggregation logic (multi-employee/multi-period averaging, empty-roster short-circuit, zero-score-rows-in-window) and the controller's request validation. A live boot (`app.listen`/`connectMicroservice`) succeeds and the new RPC is reachable over a real gRPC socket - but a full live call could not be exercised end-to-end in this session, since `EmployeeGrpcClientService.getSchedulableRoster` depends on core's own gRPC server (port 5000), confirmed unreachable in this sandbox (the same pre-existing environment gap ADR-0115 already found). The server-side failure surfaces as a generic `2 UNKNOWN` gRPC error today, not a typed "unavailable" response - acceptable as-is, since Module 10's own client wrapper (`ComplianceGrpcClientService`) already treats any RPC failure, of any shape, as `ComplianceGrpcClientUnavailableError` (§4's degraded-mode trigger) - no special-casing needed on either side of this specific failure mode.
