# ADR-0132: SCD Type 2 history for `AIGovernancePolicy` and `AiProviderConfig`, matching Module 02's own precedent

## Context
`AiGovernancePolicy.update` and `AiProviderConfigService.configure` both upsert in place - every prior autonomy-level setting or BYOK provider configuration was silently overwritten with no audit trail of what changed, by whom, or when. For a governance-sensitive, RBAC-gated pair of mutations (ADR-0130), this is a real gap: an incident review ("who enabled `auto_execute_low_risk` and when") or a compliance audit ("which LLM provider was this tenant's data sent to during period X") had no historical record to consult.

This platform already has a real, established answer to "how do we version a row" - Module 02's `OrgUnit`/`Employee` entities use SCD Type 2 via a companion `_history` table, maintained by a Postgres trigger, append-only (ADR-0009). A different flavor exists too: `Policy` (ADR-0006) versions itself in-place in the same table via a `policyGroupId`/`version`/`effectiveFrom`/`effectiveTo` lineage, used when each version is itself a directly-addressable API resource. Neither `AIGovernancePolicy` nor `AiProviderConfig` fits the `Policy` shape - both are read on the hot path (`AiGovernancePolicyResolverService.resolve` on every recommendation, `AiProviderConfigService.resolveForCall` on every LLM call), and history is a secondary audit trail, not something a client addresses directly - the same shape as Org/Employee.

## Decision
- **Own copy of Module 02's trigger + companion-table pattern** (ADR-0009): `ai_governance_policy_history`/`ai_provider_config_history`, `valid_from`/`valid_to` (nullable = current version), a partial unique index enforcing exactly one open version per live row, `agno_ai_app` granted `SELECT, INSERT` + a column-scoped `UPDATE (valid_to)` only - no `DELETE`, ever. Written exclusively by `AFTER INSERT OR UPDATE` triggers, never by application code.
- **`ai_governance_policy_history` versions only on a real change** to `autonomy_level`/`risk_threshold_config` (`IS DISTINCT FROM`), matching Org/Employee's own "only track meaningful column changes" convention - a tenant resubmitting an identical value is a no-op, not audit noise.
- **`ai_provider_config_history` versions on every update, unconditionally** - a deliberate departure from that convention, forced by a real constraint: `AiProviderCredentialCipherService` uses a random IV per encryption, so `encrypted_api_key`'s own column value differs even when the tenant resubmits the byte-identical plaintext key. There is no reliable way to distinguish "the key actually changed" from "the same key was re-encrypted" by comparing columns, so every `configure()` call - including a pure key rotation with no other change - is treated as a real, audit-worthy configuration-change event.
- **`encrypted_api_key` is never copied into history at all.** Only `provider`/`model`/`base_url`/`updated_by` are retained. Keeping old encrypted keys around indefinitely - even encrypted - needlessly expands blast radius if the encryption key itself is ever compromised; the history answers "which provider/model was configured, by whom, when," not "what was the key."
- **Both history tables are exposed read-only via GraphQL** (`aiGovernancePolicyHistory(actionType)`, `aiProviderConfigHistory`), newest-first, deliberately ungated - reading a tenant's own history is no more sensitive than reading its current value, the same posture `aiProviderConfig`'s own read already has.

## Consequences
- A tenant (or this platform's own future audit tooling) can now answer "what was our autonomy level for `reallocation` before last Tuesday" or "which provider were we using during the incident window" - previously unanswerable.
- `ai_provider_config_history`'s own "version on every update" posture means a tenant who rotates their API key weekly accumulates one history row per rotation, all with identical `provider`/`model`/`base_url` - a real, disclosed volume characteristic, not a bug, and not expected to be large in practice (key rotation is not a high-frequency operation).
- Live-verified against the real Postgres database used throughout this module's build: a real INSERT + two real UPDATEs proved the trigger correctly opens/closes versions, that an identical-value resubmission to `ai_governance_policy` creates no extra row, and that a key-only rotation to `ai_provider_config` (different ciphertext, same provider/model) does create a new version, exactly as designed.
- If a future need arises to also version `AiRecommendation` or another table, this is now a documented, repeatable pattern (trigger function + companion table + append-only grants) rather than a one-off.
