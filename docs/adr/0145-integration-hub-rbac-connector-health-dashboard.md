# ADR-0145: Integration Hub's RBAC pass gates the two credential-adjacent mutations; the connector health dashboard is a read-side aggregate, not a new subsystem

## Context

Every prior phase of this module left every GraphQL query/mutation on `TenantContextService`'s header-trust placeholder (ADR-0014) - no service in this build has its own identity/JWT verification infrastructure, and this module is no exception. `docs/module-12-phase-2-design-doc.md` through Phase 7's own doc comments all name this explicitly as deferred to "this module's own Phase 8-equivalent RBAC pass," pointing at ai-layer-service's ADR-0130 as the established precedent: a separate deployable service verifies tokens issued by the root platform-core service via remote JWKS (`jose`'s `createRemoteJWKSet`, real OIDC Discovery), rather than fabricating its own identity system.

Two real, unresolved questions before writing code: which of this module's mutations actually carry the kind of risk that justified ai-layer-service gating only two of its own operations rather than everything at once, and what "connector health dashboard" (§7's own phrase) concretely means for a module with no frontend in this repo.

## Decision

**RBAC**: own copies of ai-layer-service's full guard trio - `AccessTokenGuard` (remote JWKS, `CORE_JWKS_URI`/`OIDC_ISSUER`/`OIDC_AUDIENCE`), `PermissionsGuard` (`@RequirePermissions(...)` against the JWT's flat `permissions` claim), `TenantTokenMatchGuard` (cross-checks the JWT's `tenant_id` claim against `TenantContextService`'s own header-derived tenant, closing the same spoofed-header hole ai-layer-service's own ADR-0133 identified). Two mutations gated: `createConnector` (`integration_connector:write`) and `createWebhookSubscription` (`webhook_subscription:write`) - the two writes in this module's entire schema that produce a real credential or a real signing secret. Every other query/mutation (`connectors`, `syncJobHistory`, `updateFieldMapping`, `createFieldAuthorityPolicy`, `triggerManualSync`, `testWebhook`, `webhookDeliveries`, `webhookSubscriptions`, the new `connectorHealth`/`connectorsHealth`) remains on the placeholder - the same "gate the specific escalating risk, not everything at once" scoping ai-layer-service's own ADR-0130 applied to its first two gated mutations, not a claim that the rest are unimportant.

`integration_connector`/`webhook_subscription` are registered as real resources in core's own `run-seed.ts` `RESOURCES` array - the one place a new resource needs registering for its permission strings to be real, grantable things through this platform's one actual RBAC-management surface, rather than opaque strings this module's guard happens to check with nothing on the other end able to hold them. Both are automatically granted to `platform_admin` (every permission) and `tenant_admin` (every permission except `tenant:delete`) by the same generic role-binding logic every other resource already uses - no special-casing needed.

**Connector health dashboard**: `connectorHealth(connectorId)`/`connectorsHealth` (`ConnectorHealthResolver`) - a read-side aggregation over data every prior phase already made real (`IntegrationConnector`'s own `status`/`lastSyncAt`/`lastSyncStatus`, its recent `SyncJob` history, and - for `acd` connectors - whether `StreamingRelayService`'s latest streaming `SyncJob` is currently `running`). No new table, no new write path - this module has no frontend in this repo for a literal "dashboard" to render into, so the real deliverable is the single aggregating query a future dashboard UI (or an operator's own GraphQL client) would call instead of issuing N+1 separate queries per connector.

**Observability**: `integration_hub_rbac_denials_total{reason}` (own copy of ai-layer-service's identical counter, closing the exact gap that module's own ADR-0130 disclosed and left open - "Guards run before `HttpMetricsInterceptor`... no counter anywhere for RBAC denials" - closed here from the start instead of repeating that gap) and `integration_hub_webhook_deliveries_total{outcome}` (the dashboard-visible counterpart to each `WebhookDelivery` row's own `retryCount`/`deliveredAt`).

## Consequences

- `createConnector`/`createWebhookSubscription` now require a real Bearer JWT from core, correctly-scoped permission, and a matching tenant claim - a caller that previously only needed the `x-tenant-id` header now needs all three. Every other mutation/query in this schema is unaffected.
- No revocation check (same disclosed, bounded trade-off ai-layer-service's own ADR-0130 already accepted) - a revoked-but-not-yet-expired token still passes `AccessTokenGuard`, mitigated by short access-token TTLs set at the issuer, not by this service.
- Verified live: a real local JWKS server (a freshly generated RSA keypair, `jose.exportJWK`), real signed JWTs (`jose.SignJWT`) for the full scenario set ADR-0130 itself established - valid+correct-permission+matching-tenant success, missing Authorization header, wrong signing key, expired token, missing permission, and spoofed-tenant mismatch - each guard's own `canActivate` exercised directly against a hand-built `ExecutionContext`, not reimplemented or mocked.
- The connector health dashboard adds zero new failure modes to any write path - it is exclusively additive read composition over `IntegrationConnectorsService`/`SyncJobsService`, both already fully tested by every prior phase.
