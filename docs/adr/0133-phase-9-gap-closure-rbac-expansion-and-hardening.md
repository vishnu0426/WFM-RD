# ADR-0133: Phase 9 — closing every code-closable disclosed gap, expanding RBAC to the full schema, and three real hardening fixes

## Context
Every readiness checklist since Phase 5 accumulated disclosed gaps rather than closing them, by design - each phase stayed scoped to its own stated goal. This phase asked the opposite question: of every disclosed gap across all 8 phases, which are genuinely closable in code, and which require a real infrastructure decision or a human this module can't fabricate? This ADR records both categories, plus three real bugs found and fixed while investigating.

## Decisions

**RBAC expanded to every write-adjacent operation** (previously only `configureAiProvider`/`updateGovernancePolicy`, ADR-0130): `ai_interaction:write` gates the five `AIInteraction`-generating queries (`explainSchedule`/`explainForecast`/`explainReallocation`/`rootCauseAnalysis`/`askQuestion` - each has a real LLM-cost side effect despite being a GraphQL `Query`); `ai_recommendation:read`/`:write`/`:approve` gate `pendingRecommendations`/`createReallocationRecommendation`/`decideRecommendation` as three *distinct* permissions, following the `backdated_leave_entry:approve` precedent (Module 06) of giving a consequential approve/reject action its own grantable permission separate from creation. Three pure-read queries stay deliberately ungated (`aiProviderConfig`, `aiGovernancePolicyHistory`, `aiProviderConfigHistory`, ADR-0132) - reading a tenant's own already-configured value or its own history is no more sensitive than any other tenant-scoped read.

The manual `assertTokenTenantMatches(claims, tenantId)` call every gated resolver had to remember to make was promoted to a real third guard, `TenantTokenMatchGuard`, added to every `@UseGuards(...)` list - a future gated resolver can no longer forget the tenant cross-check by omission.

**A real, newly-discovered observability gap, closed**: NestJS Guards run *before* Interceptors in the request lifecycle, so `HttpMetricsInterceptor` never saw a single 401/403 any of Phase 8's new guards produced. `ai_rbac_denials_total{reason}` is now recorded directly inside `AccessTokenGuard`/`PermissionsGuard`/`TenantTokenMatchGuard` themselves - the only way to observe a Guard-thrown rejection at all. Live-verified via `/metrics` showing real, distinct counts for `unauthenticated` and `forbidden_tenant_mismatch` after real GraphQL calls.

**A real, separate bug found while building Phase 8's dashboard, fixed here**: `observability/prometheus.yml` never had a scrape target for ai-layer-service (port 8700) at all - the dashboard's own `job="agno-wfm-ai-layer-service"` panels had nothing to read from. Added, alongside this platform's first-ever Prometheus alerting rules file (`observability/alert-rules-module-10.yml`) - four rules scoped to this module's own security-relevant metrics (cross-tenant data assembly, RBAC denial spikes, circuit breaker opens, LLM error-rate spikes), not a retrofit of alerting for every other module's own dashboard.

**Two real, adversarially-motivated hardening fixes to ADR-0131's own disclosed findings**:
- `confidenceIndicator`'s groundedness check now redacts `reason`/`question` (the untrusted free-text fields) from its own comparison baseline before checking numeric-token overlap, at any nesting depth. Previously, a `reason` field fabricating specific-sounding figures ("employee e-42", "q-7") that existed nowhere in real structured data could still score full groundedness, because the serialized `inputContext` being compared against *included `reason`'s own text* - a fabricated number trivially "matched itself." Proven closed with the exact adversarial scenario ADR-0131 disclosed: the same attack that previously crossed a `minConfidenceIndicator: 0.7` threshold now scores 0.5 and correctly fails it.
- `AiRecommendationService.createFromInteraction` now runs `detectSuspiciousRationalePhrases` (a disclosed, incomplete heuristic - five phrase categories: claimed prior approval, discouraged review, claimed prior execution, urgency pressure, apparent instructions to the system) over the generating interaction's `outputText`. A match forces `requiresHumanApproval: true` regardless of autonomy level - the same "any failed criterion falls back to `approve_required`" posture §3 already established for `RiskThresholdEvaluatorService`, extended to this new criterion. The match itself is stored (`suspiciousLanguageFlags`) and surfaced to the human reviewer via GraphQL, never silently swallowed.

**Two real, narrow validation guardrails**: `askQuestion`'s `question` is capped at 4000 characters (a real cost/DoS control - nothing upstream bounded it, and every question triggers a billed LLM call) rejected before the gRPC fan-out cost of resolving its source; `configureAiProvider`'s Ollama `baseUrl` is validated as a well-formed `http`/`https` URL before ever reaching `OllamaReachabilityChecker`'s real network call, giving a clear, immediate error for an obvious typo instead of a generic fetch failure.

**A real, narrow closure of ADR-0129's "never validates Ollama reachability" disclosure**: `OllamaReachabilityChecker` probes `GET {baseUrl}/api/tags` (Ollama's own stable, unauthenticated model-listing endpoint) at `configure()` time, with a 5s timeout. An unreachable instance is rejected immediately with the real network error, rather than silently accepted and only discovered broken on the first real interaction. Explicitly disclosed as validating reachability **at configuration time only, from this service's own network vantage point** - not a standing guarantee against a firewall change or the instance going down later.

**A real structural cleanup**: `src/auth/` now has its own `AuthModule`, matching every other concern in this service (`ai/`, `graphql/`, `grpc/`, `nats/`) - previously the only concern registered as three loose providers directly inside `AiGraphQLModule`. (A real, observed NestJS DI quirk meant the three guards still also needed re-registering directly in `AiGraphQLModule`'s own `providers` for `@UseGuards(GuardClass)` to resolve reliably in practice - disclosed in that module's own comment rather than silently worked around, since it contradicts the documented "import + export is sufficient" pattern.)

**One investigated, explicitly NOT closed**: a real JWT revocation check via core's own `POST /oauth/introspect`. Investigated in depth - the endpoint requires the caller to authenticate as a registered `OAuthClient`, and every `OAuthClient` row is tenant-scoped (`tenant_id NOT NULL`, no platform-wide/system client concept exists anywhere in this schema). ai-layer-service is a cross-tenant backend service with no way to hold "the right client credentials for whichever tenant's token just arrived." Closing this for real would require a coordinated schema/architecture change to core's own OAuth client model (a non-tenant-scoped service-client concept) - out of this module's own scope, and not something to fake with a workaround that would either be broken or misrepresent its own trust model.

## Consequences
- 186 unit tests, up from 175 at the start of this phase - all touching genuinely new, real behavior (RBAC coverage, SCD triggers verified live, the confidenceIndicator fix proven against the exact prior exploit, the suspicious-language fail-closed override, Ollama reachability in both directions).
- Every RBAC scenario (missing token, wrong permission per distinct `:read`/`:write`/`:approve` permission, tenant mismatch, success with a real DB write) was live-verified against a real ephemeral JWKS server and real signed JWTs, not just unit-tested - consistent with this module's own build convention since Phase 2.
- The remaining standing items across this module's entire build: the real security/red-team review of §5 itself (never something a build phase substitutes for), and the JWT revocation gap above, which needs a decision at the platform-core level, not this module's own.
