# Module 09 Phase 2 Production Readiness Checklist

Honest split between what this phase's code actually delivers and what is genuinely a later phase's work, matching every prior module's phase checklist format and honesty bar. This phase's own design doc records four real corrections implementation surfaced (an incorrect `mv_lineage` grain, a `docker-compose.yml` assumption that contradicted the platform's own existing disclaimer, a writer-role correction, and a real constraint-violation bug) - all four are fixed here, not deferred.

## Delivered in this phase (application code)

- [x] `1700005000000-AdherenceForecastTrendRollupTables.ts`: `analytics_mv.mv_adherence_trend_rollup`/`mv_forecast_accuracy_trend`, each with RLS (`tenant_isolation`, ADR-0002 - unlike `mv_lineage`, both carry real tenant data), an idempotent-upsert unique key, and a `SELECT`-only grant to `agno_analytics_app`. Amends `mv_lineage.source_description` for `mv_adherence_trend_rollup` to the tenant/period grain actually shipped (§2.2's original framing assumed an org-unit breakdown `adherence_score` cannot support).
- [x] `migrator-pool.provider.ts` (primary) / `migrator-replica-pool.provider.ts` (replica, session timezone fixed to UTC) - two `agno_migrator` pools, contained entirely within `RefreshModule`, never exported or injected outside it.
- [x] `MvAdherenceTrendRollupRefreshJobService` / `MvForecastAccuracyTrendRefreshJobService` - two `@Cron` jobs (`0 2 * * *` / `30 2 * * *`), each reading its source table via the replica pool and upserting via the primary pool inside one transaction, updating `mv_lineage` in the same transaction. Both are idempotent/resumable (§2.2 rule 4) via their table's own upsert-key `ON CONFLICT`.
- [x] `data_as_of` sourced from each job's own real observation timestamp (`max(adherence_score.computed_at)` / the day-bucketed `evaluated_at`), never a nominal period boundary - a real bug (using `period_end`, which can be later than "now" for an in-progress month) was caught by this table's own `mv_lineage_data_as_of_not_after_refresh_check` in real verification and fixed, with a regression test guarding it.
- [x] `MvFreshnessMonitorService` - a five-minute `@Cron` sampling `mv_lineage.refreshed_at`-vs-cadence and real streaming-replication lag (`pg_is_in_recovery()`/`pg_last_xact_replay_timestamp()`), independent of whether either refresh job's own tick ran - `analytics_mv_refresh_lag_seconds`/`analytics_replica_lag_seconds` (declared in Phase 1) are wired for real as of this phase.
- [x] `app.module.ts` gains `ScheduleModule.forRoot()` and `RefreshModule` - a real DI wiring bug (`RefreshModule` not importing `MetricsModule`, surfacing only on a real app boot, not in unit tests) was caught and fixed.
- [x] Unit test coverage: migration shape (RLS, upsert keys, SELECT-only grants), both refresh jobs' query/upsert/transaction/rollback logic and their `tick()` overlap guard and failure-marking path, the freshness monitor's per-view/replica-lag sampling including the disclosed unlabeled-Gauge-defaults-to-0 prom-client behavior - all mocked-pool, no live Postgres required to run `npm test` (44 tests total, up from 20 in Phase 1).
- [x] Verified against a real local Postgres, and against a **genuine streaming physical replica** (`pg_basebackup -R` against the real primary - not simulated): both refresh jobs correctly aggregated real `AdherenceScore` rows and seeded `ForecastAccuracyLog` rows read through the replica, wrote correct upserts through the primary, and updated `mv_lineage` correctly; RLS correctly isolates tenants on both new tables; `agno_analytics_app` is confirmed unable to write to either (`permission denied`, SELECT-only grant enforced); the full app boots with the new `ScheduleModule`/`RefreshModule` wiring and serves `/healthz`/`/readyz`/`/metrics`.
- [x] `docker-compose.yml`/`scripts/init-roles.sql`: confirmed **no change needed** in this phase, correcting Phase 1's original assumption that a new replica container/role would be added here - `docker-compose.yml`'s own existing header already defers all read replicas to Terraform, for every service including the primary.

## Explicitly NOT done here (needs a later phase)

- [ ] **`mv_cost_vs_budget`/`mv_attrition_by_site`** - the genuinely multi-source, cross-module joins. Phase 3.
- [ ] **Any request path reading either new table.** `agno_analytics_app` has `SELECT` on both; nothing calls it - no GraphQL, no REST, no query engine of any kind exists in this service yet. Phase 4.
- [ ] **A real, Terraform-provisioned analytics read replica in any actual deployment.** This phase's own verification used a developer-provisioned local standby specifically to prove the application code's replica-reading logic is correct; it does not stand in for real infrastructure provisioning, which remains explicitly out of this codebase's scope (same gap every prior module's Phase 1 checklist already flags for Terraform/Vault generally).
- [ ] **A Prometheus alerting rule for `analytics_replica_lag_seconds`/`analytics_mv_refresh_lag_seconds`.** Both metrics are real and wired; no alert rule consuming them exists yet, and `analytics_replica_lag_seconds`'s own disclosed `0`-at-boot ambiguity (see design doc) needs a rule that accounts for it, not a naive `> threshold` check. Phase 8.
- [ ] **The consistency-check job (§2.3 rule 4)** comparing either table's aggregate against a fresh source read. Phase 8.
- [ ] **The custom-metric validation pipeline, BI connector, async exports, the NL query bridge, the §0.5 load test.** Unchanged from Phase 1's own list - Phases 5–8.
- [ ] **Real forecasting-service data in any actual deployment.** This phase's verification ran `forecasting-service`'s own already-checked-in Alembic migrations against the shared local dev database to populate `forecasting.forecast_accuracy_log` for a real test, and seeded three synthetic rows - neither is production data, and running another service's migrations was a one-time local-verification action, not a change to that service.
