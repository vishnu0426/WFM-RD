# Module 12 Phase 1 Design Doc — Integration Hub: Schema & Migrations

**Status:** Approved for implementation
**Owner:** Integration Hub pod (Module 12) — a Principal Integrations Engineer for the connector framework/rate-limit design (§5a) and the Security Architect (credential handling, §2.2 rule 1) re-engage starting Phase 2; this phase is schema design, not connector logic.
**Scope:** The full §2.1 entity set — `IntegrationConnector`, `FieldMapping`, `SyncJob`, `WebhookSubscription`, `WebhookDelivery`, `ProviderRateLimitConfig`, `FieldAuthorityPolicy` — as one migration in a new standalone deployable, `integration-hub-service/` (Node/NestJS), including `SyncJob.sync_type: streaming` from day one (per this phase's own explicit instruction in §7's build-phase list). Also stands up the minimal service skeleton needed to run and verify that migration: `agno_integration_hub_app`/`integration_hub` schema+role (ADR-0136), TypeORM data-source/runtime config, and the platform's standard `/healthz`/`/readyz`/`/metrics` + tenant-context + domain-error-filter scaffold. **No connector CRUD, no Vault integration, no OAuth callback, no batch runner or streaming relay, no rate-limit enforcement, no field-authority conflict resolution, no webhook dispatcher, no GraphQL, no REST mutation/query surface, no gRPC client into Module 05.** Those are Phases 2–8 per §7. This phase does not call Module 02/05/06 over any transport — the tenant-context middleware is the same header-trust placeholder every prior module's Phase 1 started with (ADR-0014).

Prerequisite work already done before this phase (not repeated here): `docs/module-12-provider-research.md` (sourced rate-limit/auth/event-delivery research for all 10 named providers, feeding §5a/§5c) and ADR-0134/ADR-0135 (the credential-storage and batch-vs-streaming shape decisions this schema is built around).

## Problem

Module 12 is framed by its own prompt as this platform's largest external-attack-surface concentration and the first module with two structurally different connector shapes in one bounded context. Phase 1's job is to get the schema shape right for both facts before Phase 2+ builds on top of it — three decisions worth pinning now rather than discovering as a breaking migration later:

1. **`FieldMapping`/`SyncJob`/`WebhookDelivery` have no `tenant_id` column in §2.1's literal DDL**, only a foreign key to their tenant-scoped parent (`IntegrationConnector`/`WebhookSubscription`). ADR-0002 rule 1 requires RLS and a tenant-id-first index "on every tenant-scoped table, no exceptions." Denormalizing `tenant_id` onto all three now, via ADR-0004's exact precedent (a genuine composite FK, safe because both parents are `tenant_id NOT NULL`), avoids a breaking schema change once Phase 3/6/7's queries need it.
2. **`ProviderRateLimitConfig` has no `tenant_id` at all** — it's platform-operator-maintained reference data (real per-provider research, `docs/module-12-provider-research.md`), not tenant-configured data. Getting its exemption from RLS and its narrower (`SELECT`-only) grant right now, rather than retrofitting it after a Phase 5 rate-limiter assumes write access exists, avoids both a security regression and a breaking grant change. See ADR-0136.
3. **`SyncJob.records_conflicted` must be structurally impossible on a `streaming` row** (§2.1/§2.2 rule 5) — the same "make the invariant impossible to violate at the schema layer" posture ADR-0054/`leave_request`'s backdated-reason check both established, chosen now rather than left as an application-layer-only guarantee Phase 6 could accidentally bypass.

Beyond those three, this phase follows the precedent every prior module's Phase 1 set for standing up a new deployable service: reuse the platform's existing conventions (RLS via `app.current_tenant_id`, `varchar` + `CHECK` enums per ADR-0003, tenant-id-first indexes, the two-role migrator/app split, OTel/prom-client/health scaffolding) rather than inventing parallel ones.

## Decision

A new standalone deployable, `integration-hub-service/` (Node/NestJS), sibling to every other Module 03–10 service — consistent with how each of those was stood up independently, and matching this module's own §1 tech-stack table. Runs against the already-provisioned Postgres instance, same as every other service — no new infrastructure.

**Schema** (`src/database/migrations/1700010000000-InitialIntegrationHubSchema.ts`): one migration, all seven §2.1 tables, in the new `integration_hub` schema. Tenant-id-first composite indexes on every tenant-scoped table, RLS `ENABLE` + `tenant_isolation` policy on six of the seven (ADR-0002, unchanged), `varchar` + `CHECK` for every truly enum-shaped column (ADR-0003) — `provider` is deliberately left unconstrained (§2.1 doesn't annotate it as an enum the way `connector_type`/`status` are), so onboarding a new provider adapter never needs a `CHECK`-constraint migration just to exist. Two schema-level design decisions worth calling out specifically, beyond the three in Problem above:
- **Composite FKs, not plain UUIDs, for the three denormalized-tenant-id tables** (`field_mapping_connector_fk`, `sync_job_connector_fk`, `webhook_delivery_subscription_fk`) — verified live to actually reject a tenant/connector mismatch (see Verification), not just documented as an intent.
- **`WebhookDelivery.created_at`, one addition beyond §2.1's literal column list** — the spec gives this table `delivered_at` (nullable, set only on eventual success) but nothing to order "most recent delivery attempts" by before a delivery ever succeeds. Every other history/append-log table in this platform (`core.audit_log`, this same migration's own `SyncJob.started_at`) carries exactly this kind of ordering timestamp. See Explicit Assumptions.

`ProviderRateLimitConfig` gets no RLS and a narrower grant (`SELECT` only for `agno_integration_hub_app`) — ADR-0136 records the reasoning; it is seeded/maintained by `agno_migrator`, not the running application, matching the `core.permission`/global-`Role` carve-out ADR-0002 already established.

**Entities** (`src/integrations/entities/`): seven TypeORM classes mirroring the migration's DDL exactly, each enum-shaped column backed by a real TS `enum`. These exist for query-building in later phases — nothing in this phase's request path (there isn't one) touches them yet.

**Service skeleton**: `TenantContextService`/`Middleware`/`Module` (own copy, header-trust placeholder, ADR-0014's convention), `HealthController` (`/healthz` always-200 liveness, `/readyz` Postgres-fatal readiness — no Vault-shaped asymmetric posture yet, since nothing reads Vault until Phase 2), `MetricsService`/`Controller`/`Module` (prom-client, `/metrics`), `DomainError`/`DomainErrorFilter` (typed error envelope, only the two tenant-context errors registered this phase). `MetricsService` also declares `integration_hub_relay_forward_duration_seconds` (§0.5's streaming SLO, p95 < 200ms) and `integration_hub_sync_job_duration_seconds` (§0.5's batch SLO, per-provider label) now, undocumented by any real call site until Phase 6/Phase 3 wire them — same "real but not yet consumed scaffolding" posture every prior module's Phase 1 metrics followed.

Observability: `observability/prometheus.yml` gains a scrape target for `agno-wfm-integration-hub-service` (port 8900) — added from Phase 1 itself, correcting the gap ai-layer-service's own history flagged (its scrape target was missing until Phase 9, ADR-0133).

## Verification

Verified against a real local Postgres instance (no Docker available in this environment; the existing `agno_wfm` database — already bootstrapped for every prior module via `scripts/init-roles.sql` — was extended with just the additive `agno_integration_hub_app`/`integration_hub` delta, matching what the updated `scripts/init-roles.sql` now specifies for a fresh environment):

- `npm run migration:run` executed cleanly end to end (all 7 `CREATE TABLE`, 6 `ENABLE ROW LEVEL SECURITY` + `CREATE POLICY`, every `GRANT`, in one committed transaction).
- **RLS actually scopes reads per tenant**: seeded one `IntegrationConnector` row each for two different tenants; `agno_integration_hub_app` with `app.current_tenant_id` set to tenant A saw exactly the tenant A row (`{Workday}`); set to tenant B, exactly the tenant B row (`{"Genesys Cloud"}`).
- **RLS actually blocks a cross-tenant write**: `agno_integration_hub_app` with tenant A's context set, attempting to `INSERT` a row claiming `tenant_id` = tenant B, was rejected with `new row violates row-level security policy for table "integration_connector"` (the `WITH CHECK` clause, not just `USING`).
- **Every CHECK constraint actually rejects the bad data it's meant to reject**: an invalid `connector_type` ('not_a_real_type'), a bogus `field_mapping.authority` value, and — the one this phase's Problem section calls out specifically — a `sync_type: 'streaming'` row carrying a non-null `records_conflicted` all failed with the expected constraint name. A matching `sync_type: 'incremental'` row with a conflict count succeeded.
- **The composite FK actually rejects a tenant/connector mismatch**: a `FieldMapping` row naming tenant B's id but tenant A's `connector_id` was rejected with `insert or update on table "field_mapping" violates foreign key constraint "field_mapping_connector_fk"`; the matching, correctly-scoped row succeeded.
- **`ProviderRateLimitConfig`'s asymmetric grant is real, not just documented**: `agno_integration_hub_app` attempting an `INSERT` got `permission denied for table provider_rate_limit_config`; a `SELECT` against a seeded row succeeded.
- **Schema isolation is real, not just documented**: `agno_integration_hub_app` querying `org.employee` got `permission denied for schema org` — it never even reaches a table-level check, confirming no `USAGE` grant leaked onto any other module's schema.
- The app boots cleanly as `agno_integration_hub_app` (never `agno_migrator`) and serves `GET /healthz` → `200 {"status":"ok"}`, `GET /readyz` → `200 {"status":"ok","postgres":"ok"}`, and `GET /metrics` → real Prometheus text exposition including the `http_request_duration_seconds` series generated by the `/healthz` probe itself.
- `npm test` (16 tests: entity/enum parity with §2.1, and a mocked-`QueryRunner` migration spec asserting RLS/grant/CHECK/FK invariants) and `npm run typecheck` both pass clean.

**One genuine, real finding surfaced by this verification, not specific to this module**: ADR-0002 states an unset `app.current_tenant_id` makes `current_setting(..., true)` return `NULL`, so every policy's `tenant_id = NULL::uuid` comparison is never true and a role sees zero rows — "fail closed." That holds exactly as documented in a *pristine* session that has never touched the GUC (confirmed live: `current_setting(...) IS NULL` → `true`). But once any transaction in that same session has run `SET LOCAL app.current_tenant_id = '<value>'` and committed, Postgres resets the custom placeholder GUC to an **empty string**, not back to `NULL` (confirmed live: after such a commit, `current_setting(...) IS NULL` → `false`, and a subsequent query with no fresh `SET LOCAL` throws `invalid input syntax for type uuid: ""` — a hard error, not a silent zero-row result). Under this platform's actual intended usage (`TenantScopedRepository.withTenantTransaction` always issues `SET LOCAL` as the first statement of every transaction, per ADR-0002 itself), this never surfaces — but it means the literal *mechanism* ADR-0002 describes ("returns zero rows") is only accurate for a connection's first-ever use of the GUC; every subsequent transaction on a pooled connection that skips the `SET LOCAL` step fails closed via a thrown exception instead, which is if anything a *stronger* fail-closed guarantee (an error surfaces loudly; a silently-empty result set does not) but is a factual correction to what's written, applicable retroactively to every other module's identical RLS convention — not something to fix unilaterally in this phase, but worth the platform noticing.

## Blast radius

- Entirely new directory (`integration-hub-service/`) plus three new docs (this doc, `docs/module-12-provider-research.md`) and three new ADRs (0134, 0135, 0136) — zero modification to any Module 01–10 table, migration, schema, or running code path.
- Additive edits to two shared files: `scripts/init-roles.sql` gains the `agno_integration_hub_app` role and `integration_hub` schema block (every existing role/schema line untouched); `observability/prometheus.yml` gains one new scrape job (every existing job untouched).
- No `docker-compose.yml` change — runs as a local process against the already-running Postgres instance, same posture as every other service.
- No cross-service call of any kind — nothing in this phase depends on Module 02/05/06's running code, and nothing in those services depends on this one yet.

## Rollback plan

Delete `integration-hub-service/`, revert the additive blocks in `scripts/init-roles.sql` and `observability/prometheus.yml`, drop the `integration_hub` schema (`DROP SCHEMA IF EXISTS integration_hub CASCADE;` — the migration's own `down()`), remove the three new docs/ADRs. Nothing external references this schema or service yet, so rollback is a non-event now.

## Explicit assumptions (spec was ambiguous or silent here)

1. **Service directory/schema/role name is `integration-hub-service` / `integration_hub` / `agno_integration_hub_app`**, matching the module's own title ("Integration Hub") rather than a longer name enumerating both connector shapes (contrast `attendance-leave-service`, which needed the longer form because its module prompt explicitly named two sub-domains as equally owned scope). Nothing in this module's prompt suggests the batch/streaming split should be named in the service identity itself — §0/§4 both frame it as one bounded context with two internal mechanisms, not two services.
2. **`WebhookDelivery.created_at` is added beyond §2.1's literal column list** — see Decision above. Low-risk, additive, matches every other history table's existing convention in this platform; flagged explicitly rather than silently added.
3. **`ProviderRateLimitConfig` seed rows are not inserted by this migration.** `docs/module-12-provider-research.md` records the sourced values, but seeding them is deliberately left to whichever phase first has a real consumer (Phase 5's rate limiter, Phase 6's first ACD connector) — inserting speculative reference data now, with no code reading it, risks the seed silently drifting stale before anything depends on its accuracy. The same "real but not yet consumed" posture applies to schema/entities, not to data.
4. **No table in this schema is partitioned.** `SyncJob`/`WebhookDelivery` will accumulate history over time, but neither is flagged in the module prompt as needing it the way `core.audit_log` (ADR-0005) or Module 05's `adherence_event` (ADR-0066) were, and this module's own framing gives no real-volume number to plan against yet. If Phase 8's hardening pass finds real volume data suggesting otherwise, that's a partitioning ADR at that point, not a speculative one now.
