# Module 12 Phase 2 Design Doc — Integration Hub: Connector Framework + Vault Integration

**Status:** Approved for implementation
**Owner:** Integration Hub pod (Module 12), with the Security Architect (§0) directly engaged on the credential write-path (§2.2 rule 1) and the Principal Integrations Engineer on the batch/streaming adapter-dispatch shape (§5a/§5c).
**Scope:** Per §7's own phase boundary — `IntegrationConnector` create+read (§3.1's `createConnector`/`connectors`), the Vault credential-reference discipline enforced and tested for both the OAuth and non-OAuth intake paths (§1, ADR-0134), the OAuth callback flow (§3.2), and both the batch-runner base and the streaming-relay base built together, "not a base-plus-later-variant" per §7's literal instruction. **No real provider adapters** (Phase 3/6b), **no field mapping/authority policy** (Phase 4), **no rate limiting** (Phase 5), **no webhook framework** (Phase 7), **no health dashboard/GraphQL beyond create+read** (Phase 8).

## Problem

Three real design gaps needed resolving before this phase's code could exist, none fully specified by the module prompt:

1. **§2.2 rule 1 says "a validation check... that rejects any payload attempting to store what looks like a raw credential" — but names no actual patterns.** ADR-0134 already decided this is provider-agnostic pattern matching, not a provider allowlist; this phase had to pick the actual patterns (PEM markers, JWT shape, `Bearer`/`Basic` auth headers, known vendor API-key prefixes, a generic long-opaque-string heuristic) and prove they don't false-positive on the legitimate long-string shapes `config` is expected to hold (UUIDs, Vault reference paths, and — found only by real end-to-end testing, not designed for up front — this module's own generated OAuth CSRF state token). See `src/connectors/credential-shape-guard.ts` and Verification below.
2. **Whose OAuth client is a connector's `client_id`/`client_secret`, and how does a header-less provider callback find its connector?** Resolved in ADR-0137: tenant-supplied per-connector OAuth registration (matching how real enterprise OAuth apps actually work), with `tenantId`/`connectorId` encoded directly into `state`.
3. **§2.1's `connector_type` enum has a fifth value, `custom_webhook`, that §2.2 rule 3a/3b never classifies as either batch or streaming.** Rather than guess, `src/integrations/connector-type.utils.ts`'s `isBatchConnectorType`/`isStreamingConnectorType` both return `false` for it — every caller of those two functions (the batch-runner base, the streaming-relay base) surfaces "neither" as an explicit, typed rejection, not a default guess. This is a genuine open gap for a future phase to resolve, not something Phase 2 silently decided.

## Decision

**Vault**: `src/vault/vault-client.service.ts`, a real HashiCorp Vault KV v2 HTTP client (`write`/`read`/`delete` against `{VAULT_ADDR}/v1/{mount}/data|metadata/{path}`), fails closed on every error path (`VaultUnavailableError`/`VaultSecretNotFoundError`, never a cached/default fallback — §0.5's chaos-test posture). No mock, no in-process stand-in: verified against a real local Vault dev-mode server (`vault server -dev`, installed via `brew install hashicorp/tap/vault` since Docker wasn't available in this environment — see Verification).

**Credential write-path guard**: `src/connectors/credential-shape-guard.ts`, run against the exact `config` object about to be persisted, *after* the caller's real credential-bearing fields (`credentials`, OAuth `clientSecret`) have already been extracted and sent to Vault. Applies identically on both intake paths.

**`IntegrationConnectorsService.create`** (`src/connectors/integration-connectors.service.ts`) branches on which of `credentials`/`oauth` the caller supplied (exactly one required): the non-OAuth path writes credentials to Vault and returns an immediately-`active` connector; the OAuth path writes the tenant-supplied client secret to Vault, generates `state` (ADR-0137), and returns a `pending_setup` connector plus the authorization URL to redirect to. `completeOAuthCallback` (§3.2) validates `state`, exchanges the code via `src/connectors/oauth-token-exchange.service.ts` (a real, generic RFC 6749 §4.1.3 authorization-code client — not Module 01's `openid-client`, which targets OIDC discovery and doesn't fit these providers' typical plain-OAuth2 shape), writes the resulting token set to Vault, and flips the connector to `active`.

**GraphQL** (`src/graphql/graphql.module.ts`, `src/connectors/graphql/`): `createConnector`/`connectors`, code-first Apollo, mirroring every sibling service's `formatGraphQLError`/`JsonScalar` convention exactly. `connectors` derives its tenant from `TenantContextService`, not a client-supplied `tenantId` argument — a deviation from §3.1's literal wording, matching every other resolver's "never trust a client-supplied tenant id" posture in this platform. `createConnector`'s OAuth fields are individual nullable `@Args()`, not a composed `@InputType()` — see Verification for the real bug this avoids.

**Batch-runner base** (`src/sync/batch/`): `BatchConnectorAdapter` interface + `BatchAdapterRegistry` (provider → adapter map, zero adapters registered this phase) + `BatchSyncRunnerService` (a single global `@Cron` tick across every active batch connector via the migrator-pool cross-tenant read, plus `POST /v1/integrations/connectors/{id}/sync` for a manual trigger). A connector whose provider has no registered adapter completes its `SyncJob` as `failed` with a clear `no_adapter_registered` reason — correct, expected Phase 2 behavior, not a bug.

**Streaming-relay base** (`src/sync/relay/`): `StreamingRelayAdapter` interface + `RelayAdapterRegistry` (same empty-this-phase shape) + `StreamingRelayService` (`start`/`stop`/`status`, backing `SyncJob(sync_type: streaming)` rows as connection/session windows per §2.1's own comment) + the matching REST endpoints. `liveSessions` is process-local, in-memory state (a real WebSocket/AES-session handle cannot be persisted to Postgres) — disclosed explicitly as a Phase 6+ scaling concern, not solved here.

**Shared**: `SyncJobsService` (`src/sync/sync-jobs.service.ts`) is the one place either base writes a `SyncJob` row, via the same `withTenantConnection` RLS discipline every write in this service uses.

## Verification

Everything below was run against real systems, not mocks — the same bar Phase 1 set, extended here to a second and third real external system (Vault, and a real generic OAuth token endpoint).

**Vault** (`test/integration/vault-client.spec.ts`, 5 tests): write/read round-trip, credential rotation (overwrite at the same path), `VaultSecretNotFoundError` for a never-written path and for a path after `delete`, and the §0.5 chaos test itself — pointing the client at an unreachable address raises `VaultUnavailableError` on both `read` and `write`, never a fallback.

**Connector creation** (`test/integration/integration-connectors.service.spec.ts`, 6 tests, real Postgres + real Vault): mutual-exclusivity validation, the non-OAuth path (Vault holds the real credential, `config` never contains it, status `active` immediately), the OAuth path (Vault holds the real client secret, `config` never contains it, a well-formed authorization URL, `state` matches `config.oauthState`), RLS (`findAllForTenant` never leaks another tenant's connectors), and — a real negative case — a Vault write failure during creation leaves **zero** connector rows behind (checked via the migrator role directly, bypassing RLS, so the assertion can't pass for the wrong reason).

**Full OAuth flow end to end** (`test/integration/oauth-callback-flow.spec.ts`, 4 tests, real Postgres + real Vault + a real local HTTP server implementing a generic RFC 6749 token endpoint): create (pending) → authorize → callback → active, with the real access/refresh token landing in Vault and never in Postgres; a tampered-nonce `state` rejected without ever calling the token endpoint; a `state` embedding the wrong tenant rejected; a provider-side rejection of the code surfaced as a clean `OAuthTokenExchangeFailedError` with the connector left `pending_setup`, not silently flipped to `active`.

**Batch/streaming bases** (`test/integration/sync-module.spec.ts`, 9 tests, real Postgres including the migrator-pool cross-tenant read): no-adapter-registered produces a clean failed job (both bases); a registered fake adapter's real outcome is persisted correctly; the overlap guard actually prevents a second tick from re-picking a connector with a running job; `triggerManualSync`/`relay.start` reject the wrong connector shape; the full relay `start`→`stop` lifecycle calls the adapter's `connect`/`disconnect` and completes the `SyncJob`; `relay.status` reflects the most recent streaming job.

**Real app boot + live HTTP** (not scripted as a Jest suite — run manually against the actual running process, `npm run start` equivalent, against real Postgres + real Vault): every route registers cleanly (`/graphql`, the OAuth callback, `/sync`, `/relay/*`); a real `createConnector` GraphQL mutation, `connectors` query, `POST /v1/integrations/oauth/callback`, `POST .../sync`, and all three `/relay/*` endpoints were exercised over real HTTP and returned the expected shapes/status codes for both the success and the documented-error cases (`SYNC_NOT_SUPPORTED_FOR_CONNECTOR_TYPE`, `RELAY_NOT_SUPPORTED_FOR_CONNECTOR_TYPE`, `NO_ACTIVE_RELAY_SESSION`, `no_adapter_registered`).

**Three real bugs this live-HTTP pass caught that no unit or mocked-integration test surfaced**, all fixed in this phase:
1. `HttpMetricsInterceptor` — REST-only, from Phase 1 — crashed every GraphQL request the instant this phase's GraphQL module started routing through the same global `APP_INTERCEPTOR` (`context.switchToHttp().getRequest()` doesn't return a real Express `Request` under a GraphQL context). Fixed with intraday-service's own already-proven multi-transport version (`context.getType<GqlContextType>()` branch), copied verbatim.
2. `DomainErrorFilter` — same root cause, different symptom: `host.switchToHttp().getResponse()` under a GraphQL context isn't a real Express `Response`, so calling `.status()` on it threw `response.status is not a function`, itself uncaught, turning every typed `DomainError` thrown from a resolver into an opaque 500. Fixed with ai-layer-service's own proven fix: re-throw under GraphQL context and let `formatGraphQLError` (already correctly wired) handle it.
3. A composed, nullable `@InputType()` GraphQL argument (`oauth`) was, in practice, instantiated by NestJS's argument pipeline and run through class-validator **even when the client omitted the argument entirely** — surfacing first as a false "both credentials and oauth provided" rejection, then (after adding the class-validator decorators the whitelist-mode `ValidationPipe` needs to not reject the object's own real fields) as spurious "clientId must be a string" errors on an argument the client never sent. Neither is reproducible by calling the resolver method directly in a unit test with `oauth: undefined`, since that bypasses the exact GraphQL/pipe interaction that produces the phantom object. Fixed by flattening `oauth` into individual nullable scalar `@Args()` (mirroring `ai-layer-service`'s own `configureAiProvider` precedent, which never used a composed input type for this reason) — a scalar argument omitted by the client is never routed through class-transformer at all, sidestepping the issue entirely. A defense-in-depth presence check (`clientId` truthy, not bare object truthiness) was left in `IntegrationConnectorsService.create` for any future non-GraphQL caller.

Every one of these three would have shipped invisibly behind a green test suite without the live-HTTP pass — recorded here as the reason this phase's verification bar included it, not just service-level integration tests.

## Blast radius

- Entirely new code within `integration-hub-service/` (`src/vault/`, `src/connectors/`, `src/graphql/`, `src/sync/`) plus one new ADR (0137) and this doc — zero modification to any other service.
- `package.json` gains `@apollo/server`/`@nestjs/apollo`/`@nestjs/graphql`/`graphql`/`@nestjs/schedule` — the same versions every sibling service already pins.
- `HttpMetricsInterceptor`/`DomainErrorFilter` (Phase 1 files) modified in place to fix the two real GraphQL-transport bugs above — both fixes are copies of already-proven fixes elsewhere in this platform, not novel code.
- No change to the Phase 1 schema/migration.
- `.env.example` gains `VAULT_KV_MOUNT`/`BATCH_SYNC_CRON_EXPRESSION` and a real default `VAULT_ADDR` for local dev; `VAULT_TOKEN` stays blank (a real per-environment secret, never a checked-in default).

## Rollback plan

Revert this phase's commits; Phase 1's schema/service skeleton is untouched and still boots/serves `/healthz`/`/readyz`/`/metrics` on its own. Nothing outside this service references any Phase 2 code yet.

## Explicit assumptions (spec was ambiguous or silent here)

1. **`custom_webhook` connectors have no sync mechanism at all yet** — see Problem §3. Not a batch connector, not a streaming connector, by explicit design rather than a guess in either direction.
2. **The batch runner's cron tick is a single global interval, not a per-connector custom schedule read from `IntegrationConnector.config`.** §2.1 mentions "sync schedule" as something `config` *can* hold; no shape for it was ever decided, and Phase 2's own scope ("batch-runner base") doesn't require deciding it now.
3. **No RBAC/permission guards on `createConnector`/`connectors` or any REST endpoint this phase** — this service has no identity/JWT verification infrastructure yet (Phase 1 shipped only ADR-0014's header-trust placeholder), matching every other module's own posture before its own RBAC-hardening phase (e.g. `ai-layer-service` before ADR-0130). This module's own framing (§0) calls out this module as the platform's largest credential attack surface — real RBAC here is a flagged, not-yet-scheduled gap, not an oversight.
4. **`triggerManualSync` exists as a REST endpoint (§3.2's literal named contract) but not yet as the GraphQL mutation `triggerManualSync` §3.1 also names.** Deferred alongside the other §3.1 mutations that depend on entities/write-paths this phase doesn't build (`updateFieldMapping`, `createFieldAuthorityPolicy`, `createWebhookSubscription`, `testWebhook`) — bundling GraphQL exposure with the phase that builds each mutation's real backing logic, not adding a thin wrapper ahead of it.
5. **Vault dev-mode server, started manually for this build** (`vault server -dev -dev-root-token-id=... -dev-listen-address=127.0.0.1:8200`), not wired into `docker-compose.yml`. Every other service's local-infra dependency (Postgres) is docker-composed; Vault isn't, since Docker itself wasn't available in this environment (a real, disclosed environment gap, not a design choice) — production readiness needs a real decision about how Vault is provisioned/run (`docs/production-readiness-checklist.md`'s existing "Vault (or equivalent) for credential issuance" item already flags this platform-wide).

## Out of scope for this phase (do not build yet)

- Real provider adapters of any kind (batch or streaming) — Phase 3/6b.
- Field mapping CRUD beyond the schema shipped in Phase 1, `FieldAuthorityPolicy` CRUD, conflict detection/resolution — Phase 4.
- Real per-provider rate-limit enforcement (§5a's token-bucket/sliding-window limiter, backoff-strategy executor) — Phase 5.
- `WebhookSubscription`/`WebhookDelivery` CRUD, signing, retry/backoff, auto-disable, the outbound NATS-driven dispatcher — Phase 7.
- Connector health dashboard, remaining GraphQL surface, dashboards/runbooks, chaos tests beyond the one already run against Vault — Phase 8.
