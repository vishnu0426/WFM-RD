# Module 09 Phase 2 Design Doc — Analytics & Reporting: Read-Replica Wiring & First Materialized Views

**Status:** Approved for implementation
**Owner:** Analytics & Reporting pod (Module 09), Principal Data Architect role continuing from Phase 1 for the replica-wiring specifics.
**Scope:** §8's own Phase 2 line: "Read-replica wiring + first materialized views... connect to Modules 02/03/05/06/08's read replicas; build `mv_adherence_trend_rollup` and `mv_forecast_accuracy_trend` first (single-source, simplest joins) to validate the pattern before tackling cross-module joins." Concretely: the analytics read replica connection (`agno_migrator` against `ANALYTICS_REPLICA_DB_HOST`/`PORT`, ADR-0108), two `@nestjs/schedule` cron jobs computing `mv_adherence_trend_rollup` (from Module 08's `AdherenceScore`) and `mv_forecast_accuracy_trend` (from Module 03's `ForecastAccuracyLog`), and a freshness/replica-lag monitor sampling both `mv_lineage` and streaming-replication lag independently of the refresh jobs themselves.

## Problem

Implementing this phase for real surfaced four things Phase 1's design doc got wrong or left underspecified — all four only visible once real code had to run against the real schemas:

1. **`compliance.adherence_score` has no `org_unit_id`.** Phase 1's `mv_lineage` seed (written from §2.2's prose, "re-aggregated by org_unit/period") described an org-unit breakdown this source table cannot support - confirmed against the real table (`\d compliance.adherence_score`), not assumed. `mv_adherence_trend_rollup` ships as a tenant/period trend instead; an org-unit breakdown would need a cross-module join to Module 02's `org.employees`, out of scope for a single-source phase. `mv_lineage.source_description` is amended in this phase's own migration (not silently rewritten) - same posture ADR-0099 documents for ADR-0098.
2. **`docker-compose.yml` already disclaims read replicas as Terraform's job**, platform-wide, for every service including the primary itself ("Production Postgres is provisioned via Terraform ... + read replicas + PITR - not modeled here"). ADR-0108's original consequences section assumed a new `docker-compose` container for the analytics replica; that would have been the first read-replica special-case in a file that already generically defers all of them. Corrected: no `docker-compose.yml` change in this phase or any later one. `ANALYTICS_REPLICA_DB_HOST`/`PORT` default to the primary for a pure local `docker-compose up`; real replica isolation comes from Terraform in any real deployment, or a developer's own manually-provisioned local streaming standby for verification (this phase's own real-Postgres verification used exactly that - a genuine `pg_basebackup`-provisioned hot standby, not a simulated one).
3. **The refresh jobs write via `agno_migrator`, not `agno_analytics_app`.** Phase 1 framed this module's own app role as the writer. Implementing the actual upsert surfaced the identical problem ADR-0098 already solved for Module 08: both new tables carry `ENABLE` (not `FORCE`) row level security, and a job upserting every tenant's rows in one tick needs the RLS-owner bypass only the schema owner (`agno_migrator`) has - `agno_analytics_app` would see (and be able to write) only a single tenant's rows per connection, which is not what a cross-tenant batch job needs. `RefreshModule` holds two `agno_migrator` pools (one per host, primary and replica) rather than a new role; `agno_analytics_app` is granted `SELECT` only on both new tables, reserved for Phase 4's request-scoped reads.
4. **`data_as_of` must never be derived from a nominal period boundary.** The first real run of `MvAdherenceTrendRollupRefreshJobService` against real week/month `AdherenceScore` rows failed its own `mv_lineage_data_as_of_not_after_refresh_check` - `period_end` for an in-progress month is a calendar boundary Module 08 assigns up front and can be later than "now," not an observation timestamp. Fixed to use `max(adherence_score.computed_at)` (the real wall-clock instant Module 08 wrote the row) instead - caught by a real constraint violation in real verification, not a code review guess, and now guarded by a regression test.

A fifth, smaller finding: a raw parameterized SQL bug (`$3` used both as a plain value and inside `$3 + interval '1 day'` confused Postgres's parameter-type inference, `error: inconsistent types deduced for parameter $3`) - fixed with an explicit `$3::timestamptz` cast, also caught in real verification against a real replica, not a review guess.

## Decision

**Two `agno_migrator` connection pools, one per host** (`migrator-pool.provider.ts` against the primary, `migrator-replica-pool.provider.ts` against `ANALYTICS_REPLICA_DB_HOST`/`PORT`), contained entirely within a new `RefreshModule` - the only place in this service that holds `agno_migrator` credentials at runtime. `migrator-replica-pool.provider.ts` fixes its session timezone to UTC (`options: '-c TimeZone=UTC'`) so `MvForecastAccuracyTrendRefreshJobService`'s `date_trunc('day', evaluated_at)` bucketing is deterministic regardless of the connecting session's own default timezone (ADR-0098's own discovered `date_trunc` pitfall, sidestepped here by fixing the session rather than computing boundaries in Node).

**Two `@Cron` jobs**, staggered 30 minutes apart (`0 2 * * *` / `30 2 * * *`), each: reads its source table via the replica pool (no per-tenant filter - one pass covers every tenant), upserts into its `analytics_mv` table via the primary pool inside one transaction, then updates that view's `mv_lineage` row (`refreshed_at = now()`, `data_as_of` from the source data's own real timestamp, `last_run_status`) in the same transaction. `ON CONFLICT` targets are each table's own upsert-key unique constraint (Phase 1's migration) - idempotent and resumable per §2.2 rule 4, same as every prior module's rollup job.

**A separate `MvFreshnessMonitorService`**, on its own five-minute schedule, independent of whether either refresh job's tick actually ran: samples every `mv_lineage` row's `refreshed_at` against its `refresh_cadence` (§0.5's staleness gauge) and the replica's own `pg_is_in_recovery()`/`pg_last_xact_replay_timestamp()` (§0.5's replica-lag gauge). Deliberately not folded into the refresh jobs themselves - a gauge only updated by a successful tick reads "fresh" forever if the job stops running entirely, exactly the silent-staleness failure mode §0.5 exists to catch.

## Blast radius

- New `src/refresh/` directory (two job services, the freshness monitor, both pool providers, a cadence-to-seconds constant) plus one new migration
  (`1700005000000-AdherenceForecastTrendRollupTables.ts`) creating `analytics_mv.mv_adherence_trend_rollup`/`mv_forecast_accuracy_trend` and amending `mv_lineage`'s Phase-1-seeded description for the first table.
- `app.module.ts` gains `ScheduleModule.forRoot()` and imports `RefreshModule` - additive, no existing module import removed.
- `scripts/init-roles.sql`/`docker-compose.yml`: **no change** in this phase (§0.6/ADR-0108's read-replica mechanism needs no new role, and no new container per this phase's own corrected understanding of the existing Terraform disclaimer).
- Zero modification to any Module 02/03/05/06/08 table, migration, schema, or running code - this phase only reads `compliance.adherence_score`/`forecasting.forecast_accuracy_log`, never writes them, and reads via the replica, not their primaries.
- This phase's own real verification required running `forecasting-service`'s existing (already-checked-in) Alembic migrations against the shared local dev database, since that schema had zero tables in this environment before this phase's work - a pre-existing gap in this dev environment, not a change this phase made to that service's code.

## Rollback plan

Revert `app.module.ts`'s two additive lines, delete `src/refresh/`, run this phase's migration's own `down()` (`DROP TABLE IF EXISTS analytics_mv.mv_adherence_trend_rollup/mv_forecast_accuracy_trend`) - `mv_lineage`'s amended description for `mv_adherence_trend_rollup` is not reverted by `down()` (a documentation correction, not schema), remove this doc and its checklist. Nothing outside this service depends on either new table yet (Phase 4 is the first consumer), so rollback is a non-event now.

Verified against a real local Postgres, twice over: (a) both migrations run cleanly against the already-provisioned `agno_wfm` database; (b) a genuine streaming physical replica (`pg_basebackup -R` against the real primary, not simulated) confirmed both refresh jobs read real `AdherenceScore`/seeded `ForecastAccuracyLog` rows through the replica, wrote correct aggregates through the primary, and updated `mv_lineage` correctly - including catching and fixing the two real bugs in §"Problem" above. RLS was verified directly: a tenant session reading `mv_adherence_trend_rollup` sees only its own 8 rows; switching `app.current_tenant_id` to a different tenant returns zero for the first tenant's rows; `agno_analytics_app` attempting a `DELETE` against either new table is rejected with `permission denied` (SELECT-only grant, exactly as designed). The full app boots with `ScheduleModule`/`RefreshModule` wired and serves `/healthz`/`/readyz`/`/metrics` - a real DI wiring bug (`RefreshModule` not importing `MetricsModule`) was caught and fixed by this same real-boot check, not by unit tests alone.

## Explicit assumptions (spec was ambiguous or silent here)

1. **`mv_adherence_trend_rollup` is a tenant/period trend, not an org-unit breakdown** - see Problem #1. This is a real, disclosed narrowing of §2.2's own framing, not a bug; an org-unit breakdown is explicitly out of scope for this single-source phase.
2. **No `docker-compose.yml` change, ever, for this replica** - see Problem #2. `ANALYTICS_REPLICA_DB_HOST` defaulting to the primary is the honest local-dev fallback; genuine replica isolation is Terraform's job in any real deployment.
3. **Refresh-job writes go through `agno_migrator`, never `agno_analytics_app`** - see Problem #3. `agno_analytics_app`'s `SELECT`-only grant on both new tables (from Phase 1's migration, unchanged) is correct and sufficient for what it is actually used for (Phase 4).
4. **`data_as_of` is sourced from each job's own real observation timestamp** (`adherence_score.computed_at` / the day-bucketed `evaluated_at`), never a nominal period boundary - see Problem #4, now enforced by a regression test (`mv-adherence-trend-rollup-refresh-job.service.spec.ts`).
5. **`analytics_replica_lag_seconds` reads `0` from process boot until a real replica connects**, a disclosed prom-client limitation (unlabeled `Gauge`s initialize to `0`, not "absent," unlike the labeled `analytics_mv_refresh_lag_seconds`) - documented inline in `MvFreshnessMonitorService`'s own doc comment and covered by its own test. A real alerting rule on this metric should pair it with `analytics_mv_refresh_job_runs_total`'s own activity rather than trusting `0` alone.
6. **A row with `mape IS NULL` in `forecast_accuracy_log` contributes nothing to `mv_forecast_accuracy_trend`**, rather than being coerced to `0` (which would understate error) - same "don't fabricate a result" posture as ADR-0098/0106.

## Out of scope for this phase (do not build yet)

- `mv_cost_vs_budget`/`mv_attrition_by_site` - the genuinely multi-source, cross-module joins - Phase 3.
- Any request path reading either new table. `agno_analytics_app`'s `SELECT` grant exists; nothing calls it. Phase 4.
- The custom-metric validation pipeline, BI connector, async exports, the NL query bridge, the §0.5 load test, and the consistency-check job - Phases 5–8, unchanged from Phase 1's own list.
