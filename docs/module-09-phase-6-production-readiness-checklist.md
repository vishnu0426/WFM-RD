# Module 09 Phase 6 Production Readiness Checklist

Honest split between what this phase's code actually delivers and what is genuinely a later phase's work, or a disclosed gap. This phase's own design doc records a real, confirmed gap in the thing this module was told to copy "the same pattern" from - Module 08's report generator has no `Idempotency-Key` handling at all, despite this module's own spec requiring one - and the decision to build it fresh on Postgres rather than reach for either of this platform's two existing (but unreachable-without-new-infra) idempotency mechanisms.

## Delivered in this phase (application code)

- [x] `1700008000000-AnalyticsExportTable.ts`: `analytics.analytics_export`, RLS-protected (real per-request tenant data), `agno_analytics_app`-owned (request-scoped CRUD, not a cross-tenant batch job - unlike every `analytics_mv.mv_*` table). Partial unique index on `(tenant_id, idempotency_key)` is the actual idempotency mechanism.
- [x] `MetricQueryEngineService.queryForExport` - a new public method, reusing (never duplicating) the exact whitelist check `query()` already enforces, selecting every dimension column plus the value column, bounded at `EXPORT_MAX_ROWS = 10,000` (disclosed placeholder), no `+1`-row trend logic. `query()`'s own external behavior is unchanged - verified by its full existing test suite passing unmodified after the refactor.
- [x] `AnalyticsExportService` - fire-and-forget, in-process async generation (confirmed against Module 08's actual code, not assumed), real `Idempotency-Key` handling (a repeated key returns the existing row, never re-triggers generation or inserts a duplicate), creator-only authorization.
- [x] `ExportStorageService` (own copy of Module 08's S3 pattern) + `csv.ts` (own copy of Module 08's dependency-free CSV writer) - this module's first S3/MinIO integration.
- [x] `AnalyticsExportsController`: `POST /v1/analytics/exports` (reads the real `Idempotency-Key` header), `GET /v1/analytics/exports/{id}` (poll for status, own copy of Module 08's `GET :id` pattern), `GET /v1/analytics/exports/{id}/download` (redirects to a presigned URL).
- [x] `analytics_exports_total{result}` - real, wired, verified via `/metrics` after real completed/failed exports.
- [x] Two new `DomainError` subclasses registered: `AnalyticsExportNotFoundError` (404), `AnalyticsExportNotReadyError` (409).
- [x] Unit test coverage: the migration's shape (idempotency index, RLS, the `file_uri`-only-when-completed invariant, least-privilege grants), `AnalyticsExportService` (idempotency-triggers-no-duplicate-generation, the fire-and-forget `generate` path tested directly for both success and failure outcomes, creator-only authorization, the not-ready-download guard), `MetricQueryEngineService.queryForExport` (whitelist reuse, dimension-column selection, no trend trick, filter application) - all mocked-pool/mocked-manager, no live Postgres required (129 tests total, up from 110 in Phase 5).
- [x] Verified against a real local Postgres and **real MinIO** (a genuine local S3-compatible server, installed and run for this verification, not mocked) - not just unit tests: a real export for `adherence_trend` completed end-to-end with a real `s3://` URI; the download redirect was followed to a real presigned MinIO URL and its CSV content was downloaded and hand-verified against the real 8 rows on file, including the `period_type` dimension column and a `data_as_of` column; a repeated `Idempotency-Key` returned the identical export without creating a duplicate (confirmed via direct DB inspection); cross-actor access was rejected; an export for an unknown metric was accepted (fire-and-forget), then observed transitioning to `failed` with the real error message attached; downloading a failed export was correctly rejected.

## Explicitly NOT done here (needs a later phase, or is a disclosed gap)

- [ ] **`createScheduledExport`** (§4.1's GraphQL mutation for a *recurring* export tied to a `SavedReport` config) - a materially different feature than this phase's one-shot REST export. No phase in this module's own build-phase list is explicitly assigned to build it. Flagged as a real, disclosed gap - not silently deferred, not assumed to be "the same thing" as what this phase built.
- [ ] **No reaper for a crashed mid-generation export.** A row stuck at `pending` forever if the process dies during `generate` - the same disclosed consequence Module 08's own copy of this async model accepts, for the identical low-volume/I/O-bound reasoning.
- [ ] **No retention/lifecycle job for old exports** - unlike Module 08's `ComplianceReport`, no `retention_expires_at`/`legal_hold` exists on `analytics_export`, and no S3 object or database row is ever deleted. No §5b-equivalent legal retention requirement exists anywhere in this module's own spec to build one against.
- [ ] **`EXPORT_MAX_ROWS`/cost-tier-style thresholds for exports are not load-tested** - Phase 8.
- [ ] **`askAnalyticsQuestion`.** Phase 7.
- [ ] **The consistency-check job.** Still not built. Phase 8.
- [ ] **A real S3 bucket in any actual deployment** - this phase's verification used a genuinely S3-compatible local MinIO instance (not mocked), which proves the application code is correct against real S3 semantics, but is not itself production infrastructure provisioning (same Terraform-deferred gap already flagged platform-wide).
